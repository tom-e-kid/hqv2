# 作業記録のライフサイクル管理の設計

状態: 合意済み（2026-10-23。F は 2026-10-24 に再定義）

## 要求との対応

[要求](requirements.md) の Goal を、状態ファイル、SSOT への影響の判断、要求の書式、判定スクリプト、`sweep` Skill、PR 作成時の SSOT 確認で実現する。

## 実現方法と判断理由

### A. 状態ファイル

各記録に `wip/<作業名>/status.json` を置く。

```json
{ "status": "active", "ssotImpact": true, "prs": [123] }
```

- `status`: `active`（進行中）・`paused`（保留）・`done`（完了・取りやめ）。取りやめも `done` とし、理由は記録本文に残す。
- `ssotImpact`: SSOT への影響の判断（`true`・`false`）。F の定義に従う。
- `prs`: この作業の PR 番号。PR を作成した時点で wip または pr の手順で追記する。
- 状態ファイルがない、または不正な記録は、一覧で警告し、`sweep` は削除しない。

空ファイルを目印にする案より、PR が複数ある場合や SSOT への影響を一つのファイルで表せ、差分で変化を追えるため JSON とした。一覧はスクリプトで表にする。

### B. SSOT への影響

着手時に、作業が SSOT の扱う事項（F の定義）に影響する可能性があるかを二択で判断し、`ssotImpact` に残す。影響ありなら必ず記録を作り、影響なしなら残す判断・引き継ぎ・合意の必要性からモデルが判断する。規模・工数では決めない。規則の本文は `docs/work-records.md`、SSOT と影響の定義は `docs/ssot.md` に置く。影響ありの作業は、SSOT が未定義のプロジェクトでも記録を作る（2026-10-24 ユーザー判断）。

経緯: 当初は重み 1〜3 と工数の目安で決めていたが、2026-10-23 のレビューで重み 2 と 3 の条件の重なりを指摘された。いったん SOT への影響を優先する順位で整理した後、同日のユーザー指示「重みについては工数は忘れよう。SOTに影響があるか、ないかの二択から始めるか。SOTに影響があるものは必ずwip書く。ないものはLLM判断」により二択にした。

### C. 要求の書式

`requirements.md` の見出しを Goal・Context・Constraints・Done When にする（この記録で試行中）。`design.md` は実現方法・判断理由・大枠への影響・検証方針を持つ。1ファイルの `work.md` は同じ4項目の後に実現方法とタスクを置く。

Goal・Constraints・Done When は要求の側に属するため、`design.md` ではなく `requirements.md` に置く案を推奨する。`design.md` に置くと、wip が区別している「要求」と「設計判断」が混ざる。Done When は `sweep` と wip が完了を判断する根拠にも使う。

### D. 判定スクリプト `scripts/wip.py`

Python 標準ライブラリだけで動く。保存先は `.hq/v2/settings.json` の `wip.path` に従う。

- `list`: 記録ごとの状態・SSOT への影響・PR と、状態ファイルの欠落・不正を表で出す。
- `sweepable --base <ref>`: `<ref>` の時点で `done` になっている記録を、削除できるものとして出す。`git show <ref>:<path>` で読むため、GitHub の API や取り込み方法に依存しない。
- `check-pr --base <ref> [--head <ref>]`: `<base>...<head>` の変更について、F の注意の条件と判定できない理由を返す。設定と状態ファイルは head のコミットから読む。PR 作成を止めない。

### E. `sweep` Skill

`skills/sweep/SKILL.md` を共通 Skill として追加する。wip の実行を前提にせず、記録の形式と `scripts/wip.py` を使う。

1. 取り込み先（ベースブランチ）を利用先の規約・設定から確定する。
2. `sweepable` の記録について、Done When と継続して必要な内容の反映先を確認し、記録への参照を反映先かコミットを固定した URL に付け替えて削除する。ブランチ・コミット・PR は利用先の規約と依頼の範囲で行う。
3. 削除しないが伝えるもの: 状態ファイルの欠落・不正、`done` だが未取り込み、PR がすべてマージ済みなのに `active`、Done When が未記載。経過日数だけで状態を推測しない。

開発専用の work-maintenance は、`sweep` を読む入口に作り直す。判断基準は `sweep` に一本化し、HQ 固有の処理（develop 向け PR、並行実行のロック、通知の条件、週次タスクの前提）だけを残す。名前は変えないため、週次タスクの指示文は変更不要。

### F. PR 作成時の SSOT の確認

2026-10-24 にユーザーと再定義した。当初は「SOT と実装の乖離を防ぐ」判定として、逆向きの推論（`impact-mismatch`・`sot-without-record`）も持っていたが、機械的に分かるのは「SSOT を見直す機会が抜けていないか」までであるため、目的と実現方法を揃えた。

- 用語: SSOT（Single Source of Truth、正本）に統一する。
- SSOT の定義: この Plugin では、SDD で作成・維持する PRD・FDS・ADD 等の文書を SSOT と呼ぶ。要求・仕様・設計について、合意事項と検討中の事項を記録し、個別作業の判断の基準とする。SSOT の有無と対象文書はプロジェクトごとに定める。一つのファイルに集めるのではなく、要求は PRD、基本設計は ADD のように分担で成り立つ。AGENTS.md は自動的には含めない。
- 登録: 共有設定 `.hq/v2/settings.json` の `ssot.paths`（ファイル・ディレクトリのリスト）。既定値は持たず、未指定なら SSOT 未定義として確認を適用しない。保存場所やファイル名からは推測しない。通常は `sdd.path` が入る想定。登録は「この文書を SSOT として使う」宣言で、合意の判定ではない。SSOT は育てていくもので、草案・検討中の事項も含む。`.`・絶対パス・`..` は使えない。`sdd.path` は sdd が文書を置く場所として残す。
- 影響の範囲: 対象ユーザー・提供価値・主要な振る舞い・外部との契約・責務や境界・技術方針・制約など、個別の実装判断を方向付ける事項。変更の規模や工数では判断しない。
- 注意の条件（すべて満たす場合）: SSOT が登録され PR の head に存在する。変更に含まれる作業記録に `ssotImpact: true` がある。実装（作業記録と SSOT 以外）の変更があり、SSOT の変更がない。
- 注意の形: PR 単位で1件とし、該当する記録を並べる。「乖離している」とは言わず、「SSOT の確認・更新が必要か確認して」と求める。既存の記述で足りる・以前の PR で更新済み・まだ判断を変えない、も正当な結論とする。SSOT の中の合意・検討中は判別せず、注意を受けたエージェントが内容を読んで判断する。
- 限界の明記: 注意しないことは整合の確認を意味しない。SSOT に変更がある PR も、条件に該当しないだけ。PR が記録を触ったことは、その記録の作業がこの PR で SSOT に関わる変更をしたことを意味しないため、記録の誤りを断定しない。
- 判定できない理由（注意とは別に伝える）: 状態ファイルの欠落・不正（`invalid-status`）、登録した SSOT が head に存在しない（`ssot-missing`）、設定の不正。
- 既知の緩さ: 実装の変更は作業記録と SSOT 以外のすべてを指し、README やテストだけの変更でも条件に当てはまりうる。注意だけなので許容する。

- pr Skill: PR 作成前に `scripts/wip.py check-pr` を実行し、注意と判定できない理由を本文や利用者への報告で扱う。実行できなければ記録と差分を読んで同じ観点で確認する。
- sdd Skill: 文書を作成・引き継いだら、`ssot.paths` への登録を利用者に確認して記録する。
- Plugin Hook: `PostToolUse` で `gh pr create` と PR 作成用 MCP ツールを検出し、作成された PR へ同じ判定を行って、結果を `additionalContext` でモデルに渡す。Claude Code は `hooks/hooks.json`、Codex は `hooks/codex.json` に追加し、名前は `hooks/ssot_check.py` とする。当初は `PreToolUse` でコマンドを解析して PR を作る checkout を推定したが、改行区切りの `cd` などを見落とし、シェルの書き方を網羅できないため改めた（2026-10-24）。`PreToolUse` の注意も実行結果とともに届くため、時点の違いはない。
- 判定の根拠は作成された PR にする。実行結果から PR の URL を一つ特定し、`gh pr view` で head・base のコミット ID を取得して、そのコミットで判定する。設定と状態ファイルも head のコミットから読む。作業中のリポジトリは Git オブジェクトへのアクセス手段として使い、PR のリポジトリを指すリモートがあることと、両コミットが手元にあることを確かめる。PR の特定・リポジトリの対応・`gh` の取得（失敗・タイムアウト）・コミットのいずれかが欠ければ、判定せずに未確認と伝える。黙るのは、PR の head のコミットで SSOT が未定義と確認できた場合と、注意の条件に該当しない場合だけとし、作業中の checkout の状態は根拠にしない。

Git には PR 作成のイベントがないため Git Hook は使わない。ブラウザ等で作成する PR は対象外とする。

### G. 文書と配布

- README: Skill 一覧と呼び出し例に `sweep`、作業記録の節に状態・SSOT への影響・要求の書式、利用先のセットアップに `sweep` の定期実行の項目、Hook の全体像に SSOT 確認の Hook、設定の節に `ssot.paths` を追加する。
- AGENTS.md の構成と責務、Codex マニフェストの説明、利用先の AGENTS.md の例、検証手順、CHANGELOG を更新する。
- `scripts/validate.py` の必須資源に `skills/sweep/SKILL.md` を加える。

## 大枠への影響

このリポジトリは SSOT を定義しない。AGENTS.md と README が構成・方針を記述するが、SSOT としては数えない（2026-10-24）。このため HQ 自身の PR には SSOT の確認を適用しない。共通 Skill の追加と Hook の追加により、AGENTS.md と README の構成・責務の記述を更新する。

## 検証方針

- `scripts/wip.py` の自動テスト: 一時リポジトリで状態ファイルの読み取り・欠落・不正、`sweepable` の取り込み先判定、`check-pr` の注意の条件（SSOT の定義・存在、影響ありの記録、実装と SSOT の変更）と判定できない理由、`ssot.paths`・`wip.path` の設定。
- Hook の入出力テスト: 偽の `gh` を使い、入力の種類ごとに確認する。PR の URL の有無・複数、リポジトリの不一致（同じコミットを持つ別リポジトリを含む）、`gh` の失敗・不正な出力・タイムアウト、head・base のコミットの欠落、checkout の切り替えと未コミットの設定変更が判定に混ざらないこと、別の worktree から作った PR、SSOT 未定義のリポジトリの無出力。実装を意図的に壊してテストが失敗することも確かめる。
- 既存の検証: `scripts/validate.py`、`quick_validate.py`、`python3 -m unittest discover -s tests`、`claude plugin validate .`、Codex のカタログ確認。
- 製品での確認: 両製品の新しいセッションで、PR 作成後の `PostToolUse` の注意が届くこと。実行結果（`tool_response`）の形は単体テストとは別の未検証項目として扱う。未実施なら PR に明記する。

## 合意した判断（2026-10-23）

1. 要求の書式（Goal・Context・Constraints・Done When）は `requirements.md` に置く。
2. SOT の場所は標準を `docs/` とし、`.hq/v2/settings.json` の `sdd.path` で変更できるようにする。sdd・wip・PR 作成前チェックが同じ設定に従う。（2026-10-24 の判断 7 で置き換え。`sdd.path` は sdd の文書の置き場所として残る）
3. `prs` は wip・pr の手順で追記する。
4. 既存記録3件の状態はエージェントの判断に任された。
5. PR を2つに分ける。(1) 状態・SOT への影響・書式・スクリプト（`list`・`sweepable`）・`sweep`・work-maintenance、(2) `sdd.path` と PR 作成前チェック。

## 合意した判断（2026-10-24）

6. 用語を SSOT に統一する。状態ファイルの項目は `ssotImpact` とし、既存記録も書き換える（値は変えない）。
7. SSOT は `ssot.paths` で明示し、既定値を持たない。多くは `sdd.path` が入る想定。登録は宣言であり、草案かどうかは判断しない（ユーザー: 「SSOT自体育てていくものだから、草案だろうがそれはSSOTだと思っている」）。
8. 影響ありの作業は、SSOT が未定義でも記録を作る。
9. PR 作成時の確認は F の条件・文面・限界とし、`impact-mismatch`・`sot-without-record` を外す。状態ファイルの不正は判定できない理由として別に伝える。
10. Hook は `PostToolUse` で作成された PR のコミットを判定する（B 案、条件はコミット ID での固定・対象コミットからの設定の読み取り・取得失敗の未確認扱い）。
