# プロジェクトの開発ルール

必要な部分を既存の指示へ統合する。共通の手順は Skill に任せ、このファイルには適用方針とプロジェクト固有の指定を残す。

## 大枠と作業の関係

- docs/ はプロジェクト全体の目的・主要要求・基本設計・方針・制約についての SOT。具体的な作業はその判断基準に沿って進める。
- 作業の詳細な要求・設計・受け入れ条件・進捗は作業記録、詳細な構造・動作は実装・テストに残す。
- 使用する Skill にかかわらず、大枠が変わる場合は相談・合意して docs/ を更新する。大枠の中で決める実装詳細を逐一転記しない。

## Skill の適用

- 開発初期の大枠の策定、プロジェクト全体の方針の見直しには HQ の sdd を使う。
- 一つの目的・範囲を持つ作業の具体化、実装・検証、記録・再開には HQ の wip を使う。
- 完了した作業記録の整理と状態の点検には HQ の sweep を使える。
- 落とし穴の参照・記録や、重複・古い回避策の整理には HQ の gotchas を使える。
- Git・GitHub の作業準備、コミット、取り込みには HQ の git を使う。
- PR のタイトル・本文の整理と作成・更新には HQ の pr を使う。利用先の `.hq/v2/pr.md` があれば、その指示・書式を優先する。
- AI Reviewer の指摘への対応・再確認には HQ の pr-feedback を使える。自動監視は `.hq/v2/pr-feedback.json` で明示的に有効化し、修正・push・返信・Resolve の範囲を許可する。
- CHANGELOG・バージョンの整理とリリース準備・公開には HQ の release を使う。
- 各 Skill は単独でも使える。別 Skill の呼び出しを必須にしない。短時間の明確な修正には新しい作業記録を一律に要求しない。
- 要求・設計をまとめて合意してから実行し、同じ範囲の合意を求め直さない。依頼の範囲を超えて実装へ進まない。

## 文書の配置

大枠は docs/PRD.md・FDS.md・ADD.md を基本とし、既存の同等文書を優先する。REPO・DEV・GLOSSARY は必要に応じて独立させる。

作業記録は `wip/YYYYMMDD-<作業名>/` に置く（`.hq/v2/settings.json` の `wip.path` で場所を変えた場合は、そのパスに書き換える）。状態・docs/ への影響・PR 番号は `status.json` に残す。docs/ の範囲を変える作業は必ず記録を作り、変えない作業は必要性から判断する。要求は Goal・Context・Constraints・Done When で書く。完了・取りやめた記録は継続して必要な内容を関連文書へ反映してから削除する。完了にした PR では削除せず、取り込み後の別の変更で削除する。要求・設計・タスクは分割を標準とし、短い内容は節を分けて統合してよい。作業単位はセッション単位ではない。

作業記録もコードや関連文書とともに Git 管理する。本文は現在地が分かるよう更新し、変更の経緯は Git history に残す。

プロジェクト共通の Gotchas はルートの `GOTCHAS.md` に蓄積し（`gotchas.path` で場所を変えた場合は、そのパスに書き換える）、作業の前に関連項目を確認する。個別の作業記録とは別に扱い、Skill を跨いで共有する。既存の同等の保存先があれば優先する。

## プロジェクト固有の規約

以下は Git 運用方針の記載例。既存の設定・規約へ統合し、指定ファイルを用意してから適用する。起動方法なども、ここまたは既存の開発文書に記載する。

- 変更は作業ブランチで行う。既存作業は対応するブランチを再利用し、ベースブランチへ直接コミットしない。
- 新しい作業ブランチは `<type>/<short-description>` とする。type は Conventional Commits と揃え、説明は英小文字・数字・ハイフンで簡潔に書く。例: `feat/add-notifications`。作成したツール名を示す接頭辞は付けない。
- コミットのタイトルは Conventional Commits に従う簡潔な一行とする。必要な理由は本文に残してよい。
- 作業ブランチからベースブランチへの PR を原則とする。省略はプロジェクトの許可条件または今回の明示的な指示に基づき、必要な検証を省略しない。
- 必須検証と PR 省略条件は [.hq/v2/git.md](.hq/v2/git.md) に記載する。実在しないコマンドを作らず、未実施の検証を成功扱いしない。
- 共有する既定ベースなどは [.hq/v2/settings.json](.hq/v2/settings.json)、checkout／worktree 固有の指定は Git 管理対象外の `.hq/v2/.ignore/settings.json` に置く。既定値と進行中の作業の取り込み先を区別する。

## worktree 運用

- 新規作業: ファイル変更を始める前に、確定したベースブランチから作業ブランチと専用 worktree を作成する。相談・参照だけの場合は作成しない。
- 再開: 対応する作業ブランチと worktree を再利用する。セッション開始時に今回の作業専用として用意済みの worktree も使い、重ねて作成しない。
- 配置: 基準 checkout の `.hq/v2/.ignore/worktrees/<作業名>/` とする。基準 checkout は指定がなければ Git の主作業ツリーとし、作成した worktree 内には入れ子で作成しない。作業名は英小文字・数字・ハイフンとし、既存パスと重なる場合は接尾辞で区別する。
- 長期開発系列: 別系列が必要な場合に、系列ごとのベースブランチと保持する worktree を指定する。個別作業は対象系列のベースから分岐する。
- 環境準備: 作成先でプロジェクト指定のコピー・セットアップ手順を実行する。
- 完了後: 取り込み済みで未コミット変更がなく、利用が終わった個別作業用の worktree を削除する。長期開発系列用の worktree は保持する。

上記は HQ の標準運用の記載例。変更したい項目だけ編集するか、必要な項目だけを既存規約へ統合する。長期開発系列を使う場合は、系列ごとのベースブランチと保持する worktree の具体値も記載する。対象と使用状況は Git の情報で確認し、既存変更と他セッションの作業を保全する。

## リリース方針

以下は develop／main を使う場合の例。プロジェクトの運用へ合わせて統合する。

- 通常の作業とリリース準備は `develop` から作業ブランチを作り、`develop` へ取り込む。
- 利用者に影響する変更は、同じ作業で `CHANGELOG.md` の `Unreleased` に記載する。
- リリース時に公開対象とバージョンを確定し、CHANGELOG と関連するバージョン表記を更新する。検証後に `develop` から `main` へ取り込み、そのコミットへタグを付けて公開する。
- バージョン更新は `develop` にも残す。詳細は [.hq/v2/release.md](.hq/v2/release.md)、設定値は [.hq/v2/settings.json](.hq/v2/settings.json) に置く。
