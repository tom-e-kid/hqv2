# Git・GitHub のプロジェクト固有規約

このファイルは記載例です。既存の規約へ統合し、検証と PR 省略条件をプロジェクトに合わせて具体化してから使用してください。共通手順は HQ の git に任せます。

リリースの対象・バージョン・公開条件は [release.md](release.md) へ記載します。通常の作業とリリース PR では取り込み先が異なるため、段階に応じて明示します。

## 設定

[settings.json](settings.json) は共有設定の例です。`origin`・`develop` は例示であり、実在する remote とベースブランチへ変更します。

[settings.local.example.json](settings.local.example.json) は checkout／worktree 固有の設定例です。必要な場合だけ `.ignore/settings.json` へ必要項目を転記します。`.ignore/` は Git 管理から除外します。作業開始時に確定した取り込み先を `git.branches` に記録し、既定ベースの変更で既存作業の取り込み先を変更しません。設定は値の指定であり、検証や PR の規約を緩めるものではありません。

## 必須検証

下表は未設定です。実際の適用条件・コマンド・実行ディレクトリ、または既存の手順への参照で埋めてください。「未設定」を「検証不要」と解釈しません。不要と判断した段階は、その理由を明記します。

| 段階 | 適用条件 | 必須の処理・参照先 |
| --- | --- | --- |
| コミット前 | 未設定 | 未設定。例: 変更対象に応じた lint・型チェック |
| PR 作成前／PR なしの取り込み前 | 未設定 | 未設定。例: ビルド・単体テスト |
| 取り込み前 | 未設定 | 未設定。例: 必須 CI・レビュー条件の充足 |

処理の定義は既存のスクリプト・CI を参照し、ここへ複製しません。結果を再利用できる条件と、追加変更・競合解消時に再実施する検証も必要に応じて記載します。必須検証の失敗・未実施を成功扱いしません。

## コミット前チェック

HQ のコミット前チェックを使用する場合は、Plugin の `docs/references/commit-security.md` に従い、このリポジトリで明示的に導入します。Plugin のインストールや clone だけでは Git Hook は有効になりません。`.hq/v2/settings.json` に `"commitSecurity": {"required": true}` を記録すると、未導入の checkout でセッション開始時に導入を促されます。既存の Hook 管理がある場合はそこへ組み込み、上書きしません。整形などの処理をコミット前に足す場合は、HQ の Hook を書き換えず `<Hook 名>.d/` に置き、その置き方をプロジェクトの導入手順へ記載します。

導入後はステージ済みのローカルパス・env ファイル・秘密情報らしい値を確認し、失敗を回避せず修正します。必要な例外は `.hq/v2/security.json` で対象・規則・内容の fingerprint と理由を限定し、レビューします。コピー済みコードの更新とローカルへの有効化を、プロジェクトの導入手順へ記載します。

## PR を省略できる条件

初期状態では省略条件を定めません。PR を原則とし、今回の明示的な指示、または以下を具体化したプロジェクト規約に基づいて省略します。

- 許可する変更の範囲と影響の条件。
- 省略を認めない条件。例えば、配布する成果物や認証・権限に影響する変更。
- 省略理由と検証結果を残す場所。例えば、コミット本文や既存の作業記録。

環境・テスト・配布ツールという分類だけで PR を省略しません。省略時も作業ブランチと必要な検証を維持します。PR 省略の許可は merge・push の実行許可とは分けて扱います。
