# リリース規約の記載例

この例は `develop` で変更を集め、`main` で公開する運用です。実際のブランチ・公開方法へ合わせて既存の規約に統合してください。共通手順は HQ の release を使い、git や wip の使用を前提にしません。

- 通常の作業 PR で、利用者に影響する変更を `CHANGELOG.md` の `Unreleased` に追記する。
- リリース時に対象とバージョンを確定し、作業ブランチで CHANGELOG とバージョン表記を更新する。初回バージョンと互換性を判断する契約の範囲はプロジェクトで明記する。
- 準備を `develop` へ取り込み、リリース PR で `main` へ取り込む。準備中に次回分の変更を混ぜない。並行開発が必要になったら、対象を固定する運用を別途定める。
- `main` の検証済みコミットへタグを付けて公開する。バージョン更新は `develop` にも残す。
- 緊急修正や公開途中の失敗では、開発側との整合・各公開先の状態を確認してから再開する。公開済みのタグ・同じバージョンを上書きしない。

## プロジェクトで具体化する項目

設定値は [settings.json](settings.json) の `release` に記載する。この例のブランチ名・ファイル名は例示です。次の項目は未設定であり、公開前に実在する手順を指定してください。

| 項目 | 指定する内容 |
| --- | --- |
| 初回バージョン・互換性 | 初回の番号、公開している機能・契約と破壊的変更の判断基準 |
| バージョン更新 | 対象ファイル・変更箇所・生成物の更新方法。`versionFiles` は空の例なので、必要な実在するパスを指定 |
| 検証 | [Git 規約](git.md) の必須検証に加え、リリース固有の確認と CI・承認条件 |
| 公開先 | remote・配布先、タグ命名、Release・配布の実行方法と結果の確認方法 |
| 取り込み方法 | 開発・公開ブランチの履歴を保つマージ方法と、緊急修正の反映方法 |

更新対象のファイルが存在し、設定・CHANGELOG・配布物が一致することを確認する。公開予定日は利用者のタイムゾーンを使い、延期時に見直す。リリースの準備依頼を公開の実行許可とみなさない。
