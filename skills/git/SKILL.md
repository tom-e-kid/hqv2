# Git の作業を準備し、検証して取り込む

利用先の規約に沿って Git・GitHub の操作を進める。steering の使用や作業記録の存在を前提にしない。一つの目的を一つの作業ブランチにまとめることを目安とし、記録とブランチの一対一対応は強制しない。

## 対象と規約を確認する

CWD から `git rev-parse --show-toplevel` でルートを取得する。worktree の所属や使用中のブランチは Git の情報で確認し、ディレクトリ名から推測して別の checkout へ移動しない。

依頼、AGENTS.md などの指示、参照された開発文書・検証スクリプト・CI、現在のブランチと未コミット変更、関連 PR を確認する。`.hq/v2/references/gotchas.md` や既存の同等の記録があれば、今回に関連する項目を参照する。

標準の規約文書は利用先の `.hq/v2/git.md`。設定を読む・記録する場合は [設定と保存先](references/settings.md) に従う。既存の同等の規約・設定を尊重し、依頼なく移行や二重管理をしない。設定ファイルがなくても、取り込み先などの必要事項を既存の規約や指示で確定できれば作業できる。

要求・設計の変更がある作業は、まとめて合意してから実装する。既存の合意は引き継ぎ、Git 操作の依頼から無関係な変更を増やさない。この Skill の使用だけで push・PR 作成・merge・削除を許可されたとは扱わず、依頼と既存の権限の範囲で実行する。

## 作業ブランチと worktree を準備する

変更は作業ブランチ上で行い、取り込み先ブランチへ直接コミットしない。再開では対象の作業ブランチを再利用し、毎回新設しない。別作業の変更を勝手に stash・破棄・混在させない。

新しい作業ブランチは `<type>/<short-description>` とする。type は Conventional Commits と揃え、例えば `feat/add-notifications`、`fix/handle-empty-input`、`docs/update-setup` とする。説明は英小文字・数字・ハイフンで簡潔に書く。これはブランチの命名規約であり、Conventional Commits 自体が定める形式ではない。プロジェクトの指定を優先し、作成したツール名を示す接頭辞は付けない。

新規作業ではベースの remote とブランチを確定し、対象 ref の存在と更新状況を確認してから分岐する。現在のブランチや remote の既定値だけで `main` などと決めつけない。不明で選択が作業を左右する場合は確認する。作業開始時に取り込み先を記録し、再開時は記録と既存 PR を照合する。設定変更で既存作業の取り込み先を黙って変更しない。

作業場所の準備には [worktree の標準運用と上書き](references/worktree.md) を適用する。標準は新規作業ごとの専用 worktree 作成と、既存作業の再開時の再利用。配置は基準 checkout の `.hq/v2/.ignore/worktrees/<作業名>/` とする。利用先の `AGENTS.md` または参照先の規約で指定された項目を優先し、未指定の項目には標準運用を使う。

対象と使用状況は Git の情報で確認し、既存変更と他セッションの作業を保全する。作成先で指定の環境準備を行い、ローカル設定を引き継ぐ。長期開発系列と個別作業の使い分け、転記できる規約、整理の条件も上記の参照文書にまとめている。

## コミット前チェックを導入する

HQ のコミット前セキュリティチェックの有効化を依頼された場合は、[導入手順](../../docs/commit-security.md) に従う。Plugin ルートの `scripts/setup_security.py install --repo <利用先>` で検証スクリプトを利用先の Git 管理領域へコピーし、Git の pre-commit Hook を導入する。実際のコマンドではスクリプトの配置と対象リポジトリを確認し、パスを適切に引用する。単に Plugin を読み込んだだけでは Git 設定を変更しない。先に `status` で現在の状態を確認して報告する。`install`・`uninstall` は繰り返し実行できるが、導入済みや未導入を変更の成功と取り違えない。リポジトリとして採用する場合は、共有設定の `commitSecurity.required` に採用を記録する案を示す。共有設定の変更は、ローカルの導入とは別に確認する。採用をやめる場合は宣言の削除または `false` も確認する。

既存 Hook や `core.hooksPath` があれば上書きしない。既存 Hook を併用するなら `<Hook 名>.d/` へ移してから `install` する案を、Hook 管理ツールなら `prepare` でコードをコピーして既存管理方法へ組み込む案を示す。整形などの処理をチェックの前に足す依頼では、HQ の Hook を書き換えたり `core.hooksPath` を設定したりせず、`<Hook 名>.d/` に実行ファイルとして置く。`status` は外部管理方法の実行経路を保証しないため、検証不能を有効化済みと扱わない。更新は依頼された範囲で `update` を使い、Plugin 更新だけでコピーを自動更新しない。解除は `uninstall` を使う。

導入済みの場合、チェック失敗を `--no-verify` 等で回避しない。ステージ済み内容を修正し、必要な例外は対象・規則・内容の fingerprint と理由を明示してレビューする。Plugin Hooks の存在や、このチェックの導入を他の Git 作業の前提にはしない。利用先の必須検証の指定を引き続き確認する。

## 検証してコミットする

コミット前に、今回の変更へ適用される必須の処理を利用先の規約から特定して実施する。lint・型チェック・ビルドを一律には要求せず、実在するコマンドを使用する。必須の処理が不明なら既存の文書・スクリプト・CI を調べ、それでも特定できなければ未設定として伝える。コマンドを捏造しない。

ステージした差分を確認し、無関係な変更・秘密情報・不要な生成物を含めない。コミットの単位とタイミングは利用先の規約・依頼に従う。

タイトルは Conventional Commits に従う簡潔な一行とする。例は `feat: add user auth`。必要な理由は本文に残してよく、メッセージ全体を一行に制限しない。type・scope・言語にプロジェクトの指定があれば従う。

必須検証が失敗・未実施なら、そのまま成功扱いしてコミットしない。原因を解消するか、既存の例外規約や明示的な指示に基づいて扱い、結果と未確認範囲を残す。

## PR を作成し、取り込む

作業ブランチから確定したベースブランチへの PR を原則とする。作成前に関連する既存 PR を確認し、重複作成を避ける。base/head と差分全体を確認し、必要な検証・文書更新を完了する。本文の指示・書式は利用先の `.hq/v2/pr.md` があれば従い、なければ既存の PR テンプレートを尊重する。独自書式がなければ問題と変更後の挙動、主な変更、検証結果と未確認範囲を短く示す。PR の作成・更新をまとめて扱う場合は pr を使えるが、呼び出しを必須にはしない。

PR の省略は、利用先が定める対象・条件、または今回の明示的な指示に該当する場合に限る。環境・テスト・配布ツールという分類だけで省略可能と判断しない。省略理由を残し、作業ブランチと必要な検証は維持する。PR 省略の許可を merge・push の実行許可と混同しない。

利用先が CHANGELOG の更新を求める場合は、利用者に影響する変更を同じ作業の `Unreleased` に含める。通常の作業ではリリースのバージョン確定・タグ・公開まで進めない。開発ブランチから公開ブランチへのリリース PR は、通常作業用の既定ベースではなく、利用先のリリース規約で指定された公開ブランチを取り込み先にする。

PR 作成前、または PR を省略する取り込み前に、利用先が指定した必須検証を実施する。取り込み直前には現在の差分に対して検証が有効か、必須 CI・レビューなどの条件を満たすか確認する。同じ変更と条件に対する有効な結果は再利用できるが、追加変更や競合解消で影響を受けた検証は再実施する。必須条件が失敗・未完了なら取り込まない。

依頼された段階の結果として、作業ブランチ・取り込み先、コミットや PR の参照、検証結果、未完了事項を必要な範囲で伝える。コミットだけの依頼を push や取り込みまで拡張しない。worktree の整理は利用先の指定と [標準運用](references/worktree.md) に従い、保持する場合は理由を伝える。
