# 変更をリリース単位にまとめる

利用先の方針に従い、公開対象・互換性への影響・必要な移行を明らかにしてリリースを進める。git や steering の実行履歴を前提にせず単独で使える。準備と公開を区別し、準備の依頼だけで merge・push・タグ作成・公開まで進めない。既存の依頼・合意・権限は引き継ぎ、同じ承認を求め直さない。

## 方針と対象を確認する

CWD から Git のルートを取得し、利用先の指示・リリース規約、現在のブランチ・未コミット変更、既存のタグ・Release・関連 PR を確認する。`GOTCHAS.md` や同等の記録があれば関連項目を参照する。

規約の標準保存先は利用先の `.hq/v2/release.md`。設定を読む場合は [設定と適用例](references/settings.md) を参照する。開発ブランチ・公開ブランチ・remote・バージョン更新対象・検証・公開方法を確定し、`develop`・`main`・特定の配布基盤を共通の必須条件にしない。既存の同等文書・自動化を優先し、別の仕組みを並行して新設しない。

前回の公開をタグ・Release などの根拠から特定し、対象 ref との差分と未公開の変更履歴を照合する。バージョン表記だけで公開済みと判断せず、公開履歴を確認できない場合は初回かどうかを確認する。未完了・公開対象外の変更を含めない。対象・バージョン・破壊的変更の扱いが未合意なら、理由と推奨をまとめて相談してから更新する。

## CHANGELOG とバージョンを確定する

通常の開発で蓄積した `Unreleased` を、対象差分と照合して整理する。コミットログの羅列ではなく、利用者の行動や挙動に影響する追加・変更・修正・廃止・削除・セキュリティ対応を記載する。内部変更を全件記載せず、破壊的変更には影響と移行方法を添える。変更の取り消しや重複も反映し、未公開の変更を、既に公開したバージョンの節へ追記しない。

SemVer を採用する場合は公開している機能・契約に対する互換性から major・minor・patch を判断する。コミットの type は手がかりとし、実際の変更との整合を確認する。初回バージョンや独自規約があればそれに従い、初回の予定バージョンを機能追加だけで自動的に上げない。

合意した公開範囲の内容を、バージョン・利用者のタイムゾーンでの公開予定日を付けた節に移す。次回のために `Unreleased` は残す。予定日の変更や公開の延期では内容・日付を見直し、準備段階の記録を公開の証拠にしない。

マニフェスト、パッケージ、ロックファイル、カタログ、配布説明など必要な更新対象を確認する。予定バージョンを示す箇所と、初回バージョン・過去の例などを区別し、文字列の一括置換で過去の情報を書き換えない。

## 検証し、公開ブランチへ取り込む

変更は作業ブランチで準備する。開発ブランチから公開ブランチへ取り込む運用では、準備の変更を開発ブランチへ取り込み、その確定した範囲をリリース PR で公開ブランチへ取り込む。バージョンと CHANGELOG の確定を通常の開発側にも残す。

準備中に対象外の変更が開発ブランチへ入った場合は、そのままリリース範囲を拡張しない。作業を止めて対象を再確認するか、利用先の規約で定めたリリース用ブランチで範囲を固定する。公開ブランチだけの修正がある場合も差分を確認し、取りこぼさず開発側へ反映する。

利用先の必須検証と CI・レビュー条件を確認する。CHANGELOG・バージョン・配布対象の整合を含め、追加変更や競合解消で影響を受けた検証はやり直す。失敗・未実施を成功扱いせず、条件が未完了なら取り込まない。既存 PR を確認して重複を避ける。本文は利用先の `.hq/v2/pr.md` があればその指示・書式に従い、なければ既存の PR テンプレートを尊重し、対象・バージョンの理由・利用者への影響・検証結果をまとめる。PR の作成・更新には pr を使えるが、呼び出しを必須にはしない。

## タグ・公開と再開

公開は依頼された範囲と実行権限に従う。公開ブランチへ実際に取り込まれたコミットを確認し、そのコミットにバージョンのタグを付ける。検証した内容と配布物・公開対象が一致することを確認する。

同名タグや同じバージョンの Release・配布物が既にある場合は、コミットと内容を確認する。一致すれば完了済みの段階を再実行せず、不一致なら上書き・タグの付け替え・同じバージョンの再配布をせず確認する。

途中で失敗したら、ローカルタグ・remote タグ・Release・配布先のどこまで反映されたかを調べる。公開結果が不明なまま一連の操作を再実行せず、未実行と確認できた段階から再開する。公開済みの内容を直す必要がある場合は、新しいバージョンでの修正を検討する。

結果は「準備済み・取り込み済み・タグ作成済み・公開済み」を区別し、バージョン・対象コミット・PR／タグ／公開先の参照、検証と残作業を必要な範囲で伝える。準備完了を公開完了とは報告しない。
