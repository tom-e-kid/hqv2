# リリースの設定と適用例

設定は操作対象の checkout のルートを基準に読む。共有する値は `.hq/v2/settings.json` の `release` に置き、既存の同等設定があればそれを使う。初期化を一律に要求しない。必要な項目が不明なら、指示・既存文書で確定する。

| 項目 | 意味 |
| --- | --- |
| `developmentBranch` | 変更を集約するブランチ。開発・公開ブランチを分ける場合に指定 |
| `releaseBranch` | リリース対象コミットを確定する公開ブランチ |
| `changelog` | リポジトリルートからの CHANGELOG の相対パス |
| `tagPrefix` | バージョンの前に付けるタグの接頭辞。例: `v`。空文字も可 |
| `versionFiles` | 更新対象ファイルのルートからの相対パスの配列。変更箇所や連動する生成物はリリース規約に記載 |

既存の `git` などの設定は保持する。remote は利用先の Git 規約や設定で確定し、ブランチ名だけから対象のリポジトリを推測しない。PR の取り込み先は段階によって変わり、通常の作業・準備作業は開発ブランチ、リリース PR は公開ブランチへ向ける。今回の PR の取り込み先を明示し、通常作業用の既定ベースを黙って書き換えない。

`.hq/v2/.ignore/settings.json` に `release` の上書きがあれば、明示された項目ごとに共有値より優先する。`versionFiles` の配列は全体を置き換える。形式が不正なら黙って既定値に戻さず、対象や公開範囲が共有方針と異なる場合は確認する。ローカル設定を使って必須検証や権限を緩めない。ファイルは Git 管理から除外し、認証情報を保存しない。

利用先向けの [リリース規約例](../../../examples/project/.hq/v2/release.md) と [共有設定例](../../../examples/project/.hq/v2/settings.json) を必要な範囲で既存の規約へ統合する。検証や公開の実行コマンドは `.hq/v2/release.md` または既存の開発文書へ記載し、スクリプト・CI の処理内容は複製しない。
