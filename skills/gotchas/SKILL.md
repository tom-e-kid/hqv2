# プロジェクトの落とし穴を育てる

次の作業で同じ失敗や調査を避けられるよう、発生条件・問題・対処・確認状況を利用先プロジェクトに残す。Skill の使用履歴を問わず単独で使え、別 Skill の呼び出しを必要としない。

## 保存先と参照

保存先は、利用先プロジェクトの共有設定 `.hq/v2/settings.json` の `gotchas.path` に従う。値はリポジトリのルートからの相対パスで、未指定なら `GOTCHAS.md`。値が文字列でない、空、絶対パス、`..` を含むなどの不正な場合は、標準値に戻さず問題を伝える。保存先が Git の管理対象から外れている場合は、記録する前に伝える。Plugin のインストール先には書き込まない。既存の同等の記録があれば優先し、勝手に移動・統合・重複作成しない。

まず対象領域・操作・技術名・症状やエラー文を手がかりに見出しと本文を検索し、関連項目を絞る。原因が不明でも症状から探し、見つからなければ用語を変えるか周辺カテゴリまで範囲を広げる。関連項目を確認し、現在の文書・実装・環境にまだ適用できるかを確かめる。症状が似ているだけで同じ原因と決めず、項目の発生条件と今回の条件を照合する。記録がない場合はその旨を伝え、参照だけの依頼で空ファイルを作らない。

## 残す知見を選ぶ

依頼、実際の作業結果、関連する文書・コード・ログから、次の判断や行動を変える知見を選ぶ。特に、再び遭遇する可能性があり、通常の文書やコードから気づきにくい条件・制約・挙動を残す。明示的に記録を依頼された内容はその意図を尊重する。

失敗の全ログや一般的な注意事項を集めず、調査経緯は個別の作業記録に持たせる。観測した事実と原因の仮説を区別し、未確認の原因や対処を確定事項として書かない。記録・整理の依頼だけで、新たな実験や修正を実行しない。

## 記録と更新

必要な知見が見つかった時にファイルを作成する。最初は一つのファイルで扱い、項目が増えたらテスト・配布・外部サービスなど対象領域の見出しで整理する。Skill 名を必須の分類にしない。分類は実際の項目と作業時の探し方に合わせ、空のカテゴリや固定の分類一覧を先に作らない。複数領域にまたがる項目は主な領域に置き、必要なら相互参照し、本文を複製しない。

各項目は対象・操作・症状が分かる短い見出しを付け、次を必要な範囲で記載する。既存の形式があれば尊重する。

- 検索の手がかり: 技術名・コマンド名・特徴的なエラー文など、実際の作業で使う語を見出しや本文に含める。別名は有用な場合だけ補い、根拠のない原因や無関係な語を足さない。
- 状態: 有効・未確認・解消済みなどをカテゴリと分けて示す。対処の有効性と問題が未解決であることを区別する。
- 発生条件: 対象領域、操作、環境やバージョンなど、再遭遇時に照合できる条件。
- 問題: 期待と異なる挙動、見分けるための症状。原因が仮説なら明記する。
- 対処: 有効と確認した方法とその適用範囲。未確認または未解決ならその状態を残す。
- 根拠と確認日: 関連する作業記録・文書・コードなどの参照と、事実や対処を確認した日。更新日を検証日として扱わない。

日付は利用者のタイムゾーンを使う。同じ条件・問題の項目があれば更新し、適用条件が異なるものを無理に統合しない。秘密情報や個人情報をログから転記しない。

## 整理と他の記録との分担

整理を依頼されたら、関連する項目の重複、矛盾、適用条件、現在の有効性を見直す。古いという理由だけで削除せず、根本修正や環境の変化で不要と確認できたものは、根拠とともに解消済みとして整理する。有効性を確かめられないものは未確認とする。

検索性の整理では、見出し・カテゴリ・検索語を整え、項目が増えて全体を探しにくい場合はカテゴリや項目へのリンクを持つ短い索引を設ける。並べ替え・統合時も発生条件、根拠、未確認事項と既存の参照を保持する。

定期タスクからの整理には [定期見直し](references/maintenance.md) を使う。手動でも同じ整理基準を適用し、スケジューラの導入や特定ツールの機能を前提にしない。

恒久的なルールや正式な手順になった内容は、AGENTS.md や開発文書へ反映する候補とする。反映は依頼や既存の合意の範囲で行い、範囲外なら提案に留める。反映済みなら Gotchas には参照を残し、同じ手順を二重管理しない。Gotchas の記録だけで方針・要求の合意を上書きしない。

標準メモリは補助的な想起に任せ、共有する落とし穴の正本は利用先プロジェクトの記録とする。標準メモリへの保存・同期を必須にせず、全文の複製や標準メモリの設定変更は行わない。参照先を案内する場合も利用環境の規約に従う。

プロジェクト固有の知見は利用先プロジェクトで育てる。Skill の指示自体が原因の問題や、複数のプロジェクトで通用する改善は Plugin 側の改善候補として報告し、Plugin を自動で書き換えない。

## 完了

参照だけの依頼では、関連項目と今回への適用可否を伝える。記録・整理の依頼では、変更した保存先と知見、未確認・未解決の点を伝える。記録の完了を問題の解消と扱わない。残す知見がなければファイルの作成を完了条件にしない。
