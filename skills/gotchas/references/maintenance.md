# Gotchas の定期見直し

## 対象と実行条件

対象プロジェクトと保存先、整理結果の残し方を定期タスクに指定する。標準保存先は対象プロジェクトのルートの `GOTCHAS.md`。既存の同等の記録があれば優先する。頻度は蓄積量に合わせ、例えば週1回から始める。定期タスクの登録自体は、この手順を参照しただけでは行わない。

前回の見直し対象を特定できる参照点（コミットやタスクの実行記録など）があれば、記録と関連する実装・文書・環境の変更を確認する。前回から関連する変更がなく、保留していた確認事項にも新しい根拠がなければ、書き換えず終了する。参照点が不明なら未見直しとして全体を確認し、更新日だけで省略しない。記録がなければ空ファイルを作らず終了する。

## 整理する内容

- 対象領域を軸にカテゴリと配置を見直す。分類が細かすぎる場合はまとめ、実際に探す際に必要なら分ける。
- 見出し・本文から対象、操作、症状を検索できるようにし、根拠のある技術名やエラー文を補う。索引があればリンクと対応させる。
- 同じ条件・問題の重複を統合する。条件や対処の適用範囲が違うものは保持し、統合で根拠や未確認事項を失わないようにする。
- 矛盾や古い可能性がある内容を既存の根拠と照合する。現在の有効性を確かめられなければ未確認とし、要確認の理由を残す。経過日数だけで削除・解消済みにしない。
- 恒久的なルールや正式な手順への反映候補を挙げる。反映は依頼や既存の合意の範囲に従う。

分類や表現の整理と、内容の有効性の検証を区別する。読み直しや並べ替えだけで確認日を更新せず、新たな実験・実装修正を始めない。再実行で意味のない並べ替えや日付更新を繰り返さない。

## 結果の扱い

変更は既存の作業を保全し、差分を確認できる形で残す。コミット・PR などの扱いは利用先の規約と依頼の範囲に従う。未コミット変更と干渉する場合は、その変更を上書きせず提案に留める。

整理した内容、新しく判明した要確認事項、実行失敗や必要なユーザー対応があれば通知する。変更がなく、既知の要確認事項にも進展がなければ通知を繰り返さない。次回比較に使う参照点はタスクの実行記録などに残し、Gotchas 本文に実行ログを蓄積しない。

## 定期タスクへの依頼例

対象プロジェクトと保存先を実際の値に置き換え、利用するスケジューラに登録する。整理手順は複製せず、この Skill を参照する。

> 対象プロジェクトの `GOTCHAS.md`（既存の同等の記録があればそちら）を、HQ の gotchas Skill の定期見直し手順に従って整理してください。対象領域・操作・症状から LLM が関連項目を見つけやすい状態にしてください。前回から関連する変更や新しい根拠がなければ変更せず終了してください。変更は差分で確認できる形に残し、変更、新しい要確認事項、失敗、必要なユーザー対応がある場合だけ通知してください。前回の参照点が不明なら全体を確認し、次回比較に使える参照点を実行記録に残してください。
