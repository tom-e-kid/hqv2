# 作業を具体化して進める

プロジェクトの大枠に沿って、具体的な作業の要求・設計・受け入れ条件・タスクを整理し、合意した範囲を実装・検証する。記録を残してセッションを跨いで再開できるようにする。

作業単位は一つの目的・範囲であり、セッション単位ではない。作業の中に複数の実装タスクを含めてよい。

## 現在地と大枠を確認する

依頼、プロジェクトの指示、関連する docs/、コード・テスト、対応する作業記録を確認する。対象プロジェクトのルートに `.hq/v2/references/gotchas.md` や同等の記録があれば、今回に関連する項目を確認する。docs/ があれば目的・基本設計・方針・制約の基準として扱い、作業記録で上書きしない。過去の作業記録と現在の大枠が異なる場合は、その差を確認してから続ける。

現在の会話と依頼内容を中心に、ブランチ情報や作業記録の概要・状態・現在地を合わせて対応する作業を判断する。ブランチ名は手がかりとし、作業を特定する唯一の根拠や必須条件にしない。対象が明らかなら指定を求めず、どの作業を続けるか短く伝えて既存の記録を再利用する。候補を区別できない場合だけユーザーに確認し、日付の新しさだけでは選ばない。

通常は `.hq/v2/steering/active/` の作業名と短い概要・状態から候補を絞り、対象の記録を読む。`archived/` は過去の判断の参照や作業の再開に必要な場合に確認し、毎回全記録を読まない。旧配置やプロジェクト独自の配置でも、依頼に関係する候補から確認する。

docs/ や特定の Skill の使用履歴がなくても単独で使えるが、作業に必要な目的・制約を依頼や既存資料から確認し、全プロジェクトの大枠を黙って新設しない。

## 記録の保存先と内容

新しい作業は `.hq/v2/steering/active/YYYYMMDD-<作業名>/` に置く。日付は利用者のタイムゾーンでの着手日、作業名は英小文字・数字・ハイフンとする。同名を上書きせず接尾辞で区別する。プロジェクトの指定や対応する既存記録があれば優先する。旧配置の `.hq/v2/steering/YYYYMMDD-<作業名>/` も継続して使え、一律の移行や重複作成をしない。

`active/` は取り組んでいる、または近いうちに再開する作業、`archived/` は再開を見込む当面の保留や、継続して参照する価値がある記録を置く。格納位置は探索範囲を絞るために使い、作業の状態や完了の根拠は記録内に残す。`tasks.md` または統合した `work.md` の冒頭には、候補を判断できる短い概要と状態を記載する。

標準は次の3ファイル。短い内容は `work.md` に節を分けて統合してもよい。ユーザーの指定と既存構成を優先する。
明確で短時間に完了し、残す判断や引き継ぎがない修正には新しい作業記録を一律に作らない。既存の記録があれば必要な範囲だけ更新する。

- [requirements.md の雛形](assets/steering/requirements.md): 作業の目的・範囲、具体的な要求、受け入れ条件、関連する大枠と制約。
- [design.md の雛形](assets/steering/design.md): 実現方法、影響範囲、判断理由、検証方針、大枠への影響。
- [tasks.md の雛形](assets/steering/tasks.md): 作業と状態、合意の根拠、検証結果、現在地、次の作業。

ユーザー要求、提案、仮定、未決事項、合意済みの判断を区別する。設計判断をユーザー要求として書かない。既存の基準は参照し、対象の作業の具体的な条件・差分を記載する。調査・実験では確かめる問いと終了条件を使い、実験の成功を採用の合意と扱わない。

作業記録はコードや関連文書とともに Git 管理し、変更の経緯は Git history に残す。本文は現在の要求・設計・合意・進捗・次の作業が分かるよう更新する。判断理由や検証結果は残し、変更前の全文や更新履歴を本文へ逐一複製しない。

コミットのタイミングと単位はプロジェクトの規約やユーザーの指示に従い、記録更新ごとの個別コミットは必須にしない。関連するコミットには必要な記録の更新・移動・削除も含める。

## 合意した範囲を実行する

要求・設計・必要なタスクの案をまとめて提示し、合意後に実装・実行する。ファイルごとの承認を標準にせず、タスクリストだけの独立した承認も求めない。依頼や既存記録で得た同じ範囲の合意は引き継ぐ。未決事項は実行前に必要なものと後で決められるものを分ける。

合意の対象範囲・日付・根拠となるユーザーの指示を残す。ファイルの存在、経過時間、無応答を承認と扱わない。相談・記録だけの依頼では、実装や調査の実行へ勝手に進まない。

実行中は意味のある判断・進捗・結果を更新する。変更が必要なら要求・設計・タスクへの影響を揃え、追加の合意は変更した部分に限る。合意範囲内の実装上の選択に形式的な承認を追加しない。

## 大枠を変える必要が出たら

docs/ に記載した主要要求・基本設計・方針・制約を変える場合は、変更案・理由・影響を相談し、合意した内容を該当文書と図表へ反映する。合意まで影響する実行は止めるが、独立して進められる作業は続けてよい。変更を作業記録だけに閉じ込めたり、コードの現状に合わせて大枠を黙って書き換えたりしない。

大枠の中で決められる実装詳細は作業記録と実装・テストに残し、docs/ へ逐一転記しない。広い見直しが必要なら、その相談を実装と区別して扱う。別 Skill の呼び出しを条件にせず、この Skill だけでも必要な変更の相談・反映を進められる。

## 検証と完了

対象の作業の受け入れ条件を適切な方法で確認し、プロジェクトの検証・Git・PR 規約に従う。実施した方法・結果・未実施の検証と理由を記録し、タスク完了を条件の充足の代わりにしない。

実装作業は、対象の条件の充足、関連する大枠との整合、必要な docs/ 更新を確認して完了する。相談・設計・記録だけの依頼は、その成果と未決事項が整理できれば完了でき、実装済みであることを要求しない。調査・実験は定めた終了条件と結果で判断する。未完了の条件・未反映事項があれば作業全体を完了扱いしない。

完了・取りやめの作業記録は、継続して必要な仕様・判断を関連文書へ反映し、最終の状態・理由・検証結果を含む記録が Git にコミットされていることを確認してから作業ディレクトリを削除する。未コミットの記録を削除して履歴を失わないようにし、削除と参照リンクの整理もコミットに含める。継続して参照する価値がある記録は `archived/` に保持してよい。プロジェクト独自の保存方針があれば優先し、旧配置の記録を一律に整理しない。

## 中断と再開

中断時は現在地、未決事項、合意待ちの範囲、次の作業を残す。セッションの終了だけでは `archived/` に移さず、近いうちに再開する作業は `active/` に残す。

再開を見込む当面の保留は、その状態と理由を記録して `archived/` に移してよい。archived の作業を再開するときは同じ記録を `active/` に戻す。移動では同名の記録を上書きせず、参照リンクを確認・更新する。旧配置やプロジェクト指定の記録は、その配置を尊重する。Git history にだけ残る作業の参照・再開が必要な場合は、履歴から記録を確認・復元する。

再開時は関連する記録・docs/・実装の変化を確認し、古い記録を更新して続ける。合意や完了済みの作業を形式的にやり直さない。

明示的なユーザー指示を優先する。この Skill の使用だけで公開・デプロイ・外部への送信を許可されたと扱わない。
