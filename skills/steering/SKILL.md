# 作業記録と再開

対象リポジトリに作業の現在地を残す。仕様策定に限らず単独で使い、別 Skill の実行を必須にしない。記録の依頼だけで実装や作業範囲を拡大しない。

## 保存先と構成

- 新しい作業は `.hq/v2/steering/YYYYMMDD-<作業名>/` に保存する。日付は利用者のタイムゾーンでの着手日、作業名は英小文字・数字・ハイフンを使う。同名を上書きせず接尾辞で区別する。
- プロジェクトの指定や対応する既存記録があれば優先する。既存記録を勝手に移動したり、再開時に重複作成したりしない。
- 標準は `requirements.md`、`design.md`、`tasks.md` を分ける。内容が短く、個別の参照・更新が不要なら `work.md` に要求・設計・タスクの節を分けてまとめてもよい。ユーザーの指定と既存構成を優先する。
- [雛形](assets/steering/requirements.md)、[設計の雛形](assets/steering/design.md)、[タスクの雛形](assets/steering/tasks.md) から必要な項目を使う。統合時も内容の区別を維持し、空の節を埋めるために情報を作らない。

## 内容を混ぜない

- 要求: ユーザーが求める目的・範囲・条件を記録する。提案、仮定、未確認の理解は区別し、エージェントの設計判断をユーザー要求として書かない。
- 設計: 要求に対する実現方法、代替案、判断理由、影響範囲、未決事項を記録する。要求を満たす対応を示す。
- タスク: 要求・設計から導いた作業、状態、検証結果、次の作業を記録する。タスク完了を要求の充足やユーザーの合意の代わりにしない。

## 記録と更新

依頼と既存記録から分かることは質問し直さない。相談中・合意済み・作業中・中断・完了など現在の状態を明示する。合意には対象範囲、日付、根拠となるユーザーの指示を残し、無応答やファイルの存在を合意と扱わない。

意味のある判断・進捗・検証結果を記録する。要求が変わったら設計とタスクへの影響を揃え、廃止した判断を現在の決定と混同しない。検証は実施した方法と結果を残し、未実施を成功扱いしない。

中断時は現在地、未決事項、合意待ちの範囲、次の作業を残す。再開時はそれらと関連するコード・仕様を確認し、記録が古ければ差を示して更新する。合意や完了した作業を形式的にやり直さない。

## 仕様との関係と終了

永続的な仕様文書があればリンクで参照し、作業記録を現在の仕様の代わりにしない。仕様の合意や SOT の維持方法はこの Skill で定義しない。記録した案を自動的に採用済みの仕様へ反映しない。

完了時も記録を履歴として残し、結果・未完了項目・残る制約を明示する。公開・削除・外部への送信などの権限を作業記録から推測しない。
