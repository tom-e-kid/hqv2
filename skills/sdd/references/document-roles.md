# 文書の役割

以下はプロジェクト全体の判断基準を持つための分担。各文書を詳細仕様の網羅的な台帳にしない。既存の同等文書・構成を尊重する。

| 文書 | 区分 | プロジェクト全体の粒度で持つ内容 |
| --- | --- | --- |
| PRD | 基本 | ビジョン・目的、利用者と課題、主要機能・提供範囲、主要なユーザーストーリー、成功の定義、守るべき振る舞い、重要な受け入れ基準、機能・非機能の要求と制約 |
| FDS | 基本 | 主要なユースケース・業務ルール、機能間の関係、主要なデータの概念と関係、画面・API の役割と基本方針、機能の責務・境界 |
| ADD | 基本 | システム構成と実行時の関係、技術スタック、技術選定と理由、技術的制約、性能・可用性・セキュリティなどの実現方針 |
| REPO | オプショナル | ディレクトリの責務、配置と依存境界のルール、重要な入口と配置意図 |
| DEV | オプショナル | 環境構築・起動・検証方法、コーディング・命名・テストなどの規約、Git・PR の規約 |
| GLOSSARY | オプショナル | 共通するドメイン・ビジネス・UI 用語の意味、推奨表記、日英対応 |

## 重複を避ける境界

- PRD は達成すべき結果や制約。FDS は機能上の関係と振る舞いの基本設計。ADD は実現する技術構成と理由。
- 性能は PRD に達成基準と測定条件、ADD に実現方針、DEV に確認方法。基準の数値を複製せず参照する。
- FDS のデータモデルは主要な概念・関係・守る制約。ADD は保存方式などの技術判断。全テーブル・全カラム・全 DDL を docs/ に写さない。
- FDS の画面・API は役割、主要な流れ、契約の基本方針。対象の作業の詳細な仕様は作業記録、実際の項目・エラー・スキーマなどは実装・テストや機械可読な契約を参照する。ただし、長く守るべき制約は docs/ に残す。
- FDS は機能上の責務・境界、ADD は実装コンポーネントやサービスの構成。REPO はそれらのファイル配置。全クラス・全コンポーネントの一覧は維持しない。
- ADD は開発ツールの選定理由・制約、DEV は使い方。実際のバージョン・コマンド定義は設定ファイルを参照する。
- DEV は命名の形式、GLOSSARY は単語の意味・表記。個別画面の全 UI 文言を GLOSSARY に集めない。

システム構成図は ADD、主要な機能関係・概念データモデル・画面遷移は FDS を基本とする。詳細な設計図は作業記録に置いてよい。図表を全作業で必須にせず、同じ図を重複管理しない。

## オプショナル文書を作らない場合

配置の説明が短ければ ADD の関連節、開発規約が短ければ指示ファイルや既存の開発ガイド、用語が少なければ PRD または FDS の関連節を正本にする。独立した文書へ分けたら内容を移し、元の記載は参照へ置き換える。

## docs/ に残すかの判断例

| 決定 | 記載先の目安 |
| --- | --- |
| 権限のない情報を検索結果に出さない | 長く守る基準として PRD、必要な基本設計を FDS・ADD |
| 対象の作業で追加する絞り込み条件・表示方法 | 作業記録で具体化し、詳細は実装・テスト |
| 既存方針に沿ったインデックス追加 | 作業記録と実装・テスト。大枠が変わらなければ docs/ 更新は不要 |
| 検索対象や主要なデータ関係、検索基盤の変更 | 関連する大枠への影響を確認し、合意した変更を PRD・FDS・ADD の該当箇所へ反映 |

項目名だけで機械的に分類しない。追加する条件や表示方法でも、主要要求・基本設計・制約を変えるなら docs/ を更新する。
