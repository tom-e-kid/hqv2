# 初期仕様の策定

新規プロジェクトの要件を詰める場合に読む。既存プロジェクトでは、すでにある仕様と設計を出発点にし、初期文書を作り直さない。

## 要件の整理

1. 作りたいもの、利用者、解決する課題、最初に実現する範囲を確認する。依頼や既存資料で分かることは質問し直さない。
2. 実装前に必要な決定と、後で決められることを分ける。動作、受け入れ条件、重大な制約を優先する。
3. 合意した内容を全体文書へ反映し、不明点を「未決事項」に残す。ユーザーが述べた事実と提案・仮定を区別する。

## 全体文書を作る

既存の文書構成を優先する。指定がなければ、必須の役割として次の三つを用意する。

- `docs/PRD.md`: 目的、利用者、範囲、要求、受け入れ条件。
- `docs/FDS.md`: 要求を実現する機能の振る舞い、データ・API・画面の仕様。
- `docs/ADD.md`: 技術構成、技術選定の理由、制約。

雛形は [PRD](../assets/docs/PRD.md)、[FDS](../assets/docs/FDS.md)、[ADD](../assets/docs/ADD.md) を使う。初期は内容が薄くてもよく、今回の実装に必要な事項を優先する。未記入の雛形を完成した仕様と扱わない。

REPO・DEV・GLOSSARY は必要に応じて独立させる。[文書のルール](document-rules.md) の必須・オプショナルの区分を参照する。

## 合意を得る

- 標準では関連する要求・設計をまとめて提示し、実装に進んでよいか確認する。
- 文書を作成できたことや、未決事項が空であることだけで承認済みと判断しない。
- 合意の対象、根拠となるユーザーの指示、日付を文書に記録する。未合意の状態では「案」と明示する。
- プロジェクトがファイルごとの承認を要求する場合は、その順序に従う。
- 仕様策定だけを頼まれている場合は、コード生成やパッケージのインストールへ進まない。

## 初回実装へ進む

実装を依頼され、必要な要求・設計の合意が取れたら [仕様に基づく変更開発](change-workflow.md) に進む。

すでに合意した内容はリンクで参照し、同じ範囲について再承認を求めない。初回実装で新しい設計判断が必要になった場合は、その判断を提示する。

`/kickoff` や `/scaffold` などのコマンドはこの Plugin に含まれていない。利用環境に実在すると確認できた場合のみ案内する。通常はこの Skill に自然言語で仕様策定・初回実装を依頼して進める。
