# 大枠の策定

開発初期の壁打ち、既存プロジェクトの方針整理で読む。既存の合意や文書があれば出発点にし、作り直さない。

## 相談で明らかにすること

- 誰のどの課題を解決するか、目指す成果は何か。
- 主要な機能と最初に実現する範囲、対象外にすること。
- 作業を跨いで守る振る舞い、品質・運用・事業上の制約。
- 主要な機能やデータの関係、構成要素の責務・境界。
- 技術方針、採用理由、技術的制約。

依頼から分かる範囲を案にして相談を進める。上記を一括で質問することや、全項目の確定を最初の合意条件にすることは求めない。初期は文書が薄くてもよく、重大な未決事項と後で決められる詳細を区別する。

## 永続的な文書へ残す

指定がなければ [PRD](../assets/docs/PRD.md)、[FDS](../assets/docs/FDS.md)、[ADD](../assets/docs/ADD.md) を基本とする。既存の同等文書があればそれを使う。REPO・DEV・GLOSSARY は独立して維持する必要がある場合に追加する。

[文書の役割](document-roles.md) に従い、プロジェクト全体の判断に必要な粒度で記載する。全 API 項目・全クラス・全タスクなどを先回りして埋めない。雛形の空欄を埋めるために要求や設計を作らない。

## 合意と具体化への引き継ぎ

目的・主要要求・基本設計・方針の案をまとめて相談する。合意した範囲と根拠を文書へ残し、未決事項に具体化への影響を添える。特定のファイル数や未決事項ゼロを合意の条件にしない。

仕様策定だけの依頼ではここで終了する。実装も依頼されている場合は、合意した大枠を参照して一つの目的・範囲を持つ作業の要求・設計・受け入れ条件を具体化し、合意後に実装へ進む。大枠の合意を、すべての詳細設計の合意と扱わない。
