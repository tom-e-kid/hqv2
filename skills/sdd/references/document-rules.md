# 文書のルール

## 永続的な仕様文書（SOT）

`docs/` の仕様文書は現在の合意を表す。SOT は変更できない決定ではなく、現在の参照先を一意にするもの。合意した変更を反映し、案・仮定・未決事項と区別する。

同じ事実は一か所に置き、他の文書からリンクで参照する。作業記録がある場合は今回の差分・検討過程をそちらへ残し、古い作業記録を現在の SOT と扱わない。

## 必須とオプショナル

既存の文書構成を優先し、名前を一律に変更しない。新規で指定がなければ次の構成を使う。「必須」は情報の役割を維持する意味であり、既存の同等文書と二重管理しない。

| 文書 | 区分 | 内容 |
| --- | --- | --- |
| `docs/PRD.md` | 必須 | 目的、利用者、要求、スコープ、受け入れ条件 |
| `docs/FDS.md` | 必須 | 機能の振る舞い、データ・画面・API の機能仕様 |
| `docs/ADD.md` | 必須 | 技術構成、技術選定と判断理由、技術的制約 |
| `docs/REPO.md` | オプショナル | ディレクトリ・配置の意図を独立して説明する必要がある場合 |
| `docs/DEV.md` | オプショナル | 開発規約が詳しくなり、指示ファイルから分離する場合 |
| `docs/GLOSSARY.md` | オプショナル | ドメイン用語や表記を独立して管理する必要がある場合 |

初期は内容が薄くてもよい。将来の機能を網羅せず、今回の実装に必要な要求・設計を具体化する。未決事項には実装への影響を記載し、未記入の雛形を完成・合意済みと扱わない。FDS は機能がどう動くか、ADD はその実現を支える技術構成と理由を扱う。

## 図表と合意

必要な図表を関連文書内へ記載する。Mermaid、表、ASCII を使い、画像が必要なら `docs/images/` に保存して参照する。設計変更時は関連する図表も更新する。

合意の対象・根拠・日付を記録する。文書ごとの承認は標準では求めない。日付は利用者またはプロジェクトが指定するタイムゾーンを使う。

## プロジェクトの規約

技術スタック、検証、Git・PR の規約などは対象プロジェクトの指示またはそこから参照する開発文書に置く。仕様と規約を重複管理しない。作業記録の保存・再開の手順は SOT の管理と分ける。
