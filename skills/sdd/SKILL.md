# スペック駆動開発

永続的な仕様文書を現在の合意の SOT とし、要求・設計を実装と検証の基準にする。

## 原則

- 対象プロジェクトの指示、関連する仕様、コード、既存の合意を確認する。文書の配置、技術スタック、検証・Git・PR の規約はプロジェクトの指定に従う。
- 要求・設計をまとめて合意してから実装する。依頼や既存記録に同じ範囲の合意があれば引き継ぎ、確認し直さない。
- ユーザー要求、提案、仮定、未決事項、合意済みの決定を区別する。要求を実装に合わせて黙って書き換えない。
- 合意した要求と受け入れ条件で実装結果を検証し、変更した仕様を SOT に反映する。
- 仕様を変えない軽微な修正に、新しい仕様文書や形式的な合意を追加しない。行数だけで軽微と判断しない。
- 仕様策定だけの依頼では実装へ進まない。Skill の使用だけで公開・デプロイ・外部への送信を許可されたと解釈しない。

## 作業に応じて読む

- 初期の要件整理・仕様策定: [初期仕様の策定](references/kickoff.md)。
- 初回実装、機能追加・修正: [仕様に基づく変更開発](references/change-workflow.md)。
- 仕様文書の作成・更新: [文書のルール](references/document-rules.md)。

参照先はこの Skill ディレクトリを基準に解決する。

## 作業記録との関係

既存の作業記録があれば要求・設計・合意・検証結果を参照する。記録がなくても、この Skill だけで仕様の策定・更新と開発を進められる。特定の作業フォルダ、ファイル数、別 Skill の実行を前提にしない。

仕様や合意の根拠、受け入れ条件に対する結果は対象リポジトリの関連文書に残す。作業全体の進捗管理・中断・再開は独立した手法として扱う。

## 完了時

受け入れ条件の結果、実施した検証、SOT への反映、未解決事項を報告する。未実施の検証を成功扱いしない。
