# プロジェクトの大枠を定める

スペック駆動開発の土台となる目的・主要要求・基本設計・方針・制約をユーザーと相談し、永続的な文書へ残す。これらを対象プロジェクトの北極星・SOT とする。

## docs/ が持つもの

`docs/` はプロジェクト全体の判断基準の正本。実装の全詳細を写す場所ではない。対象ユーザー、提供する価値、主要な振る舞い、設計の境界、守る制約など、個別の作業を判断するために必要な内容を記載する。

具体的な作業の要求・設計・受け入れ条件・進捗は作業記録、詳細な構造と動作は実装・テストに持たせる。docs/ に記載した方針や基本設計が変わる場合は、大きな改修か小さな修正かにかかわらず更新する。

## 進め方

- 対象プロジェクトの指示、依頼、既存文書・実装を確認する。分かっていることを質問し直さず、既存の文書名・保存先・合意を尊重する。対象プロジェクトのルートに `GOTCHAS.md` や同等の記録があれば、今回に関連する項目を確認する。
- 壁打ちしながら、実装前に決める大枠と、具体的な作業で決められる詳細を分ける。最初から全機能・全設計を確定しようとしない。
- ユーザー要求、提案、仮定、未決事項、合意済みの判断を区別する。未合意の案で現在の方針を置き換えない。
- 要求・基本設計の案をまとめて提示し、必要な合意を得て文書へ反映する。ファイルごとの承認を標準にしない。依頼や既存記録で得た同じ範囲の合意は確認し直さない。
- 仕様策定だけの依頼では実装・環境構築へ進まない。実装も依頼されている場合は、大枠の合意後に対象の作業の要求・設計を具体化して進める。

## 必要に応じて読む

- 初期の壁打ちと文書作成: [大枠の策定](references/kickoff.md)。
- 既存の大枠の見直し: [方針の見直し](references/direction-review.md)。

参照先はこの Skill ディレクトリを基準に解決する。

## 作業記録との関係と完了

既存の作業記録があれば検討材料として参照するが、特定の保存先・別 Skill の実行を前提にしない。文書を作るだけで合意済みとせず、合意範囲・根拠・未決事項を残す。

依頼された大枠が文書化され、その合意状態と具体化へ進める範囲が明らかになれば、仕様策定の作業は完了できる。実装済みであることは条件にしない。ユーザーに決定事項、未決事項、後の作業で決める内容を報告する。
