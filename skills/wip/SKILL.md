# 作業を具体化して進める

プロジェクトの大枠に沿って、具体的な作業の要求・設計・受け入れ条件・タスクを整理し、合意した範囲を実装・検証する。記録を残してセッションを跨いで再開できるようにする。

作業単位は一つの目的・範囲であり、セッション単位ではない。作業の中に複数の実装タスクを含めてよい。

## 現在地と大枠を確認する

依頼、プロジェクトの指示、関連する docs/、コード・テスト、対応する作業記録を確認する。Gotchas の記録（`.hq/v2/settings.json` の `gotchas.path`、未指定は `GOTCHAS.md`）や同等の記録があれば、今回に関連する項目を確認する。docs/ があれば目的・基本設計・方針・制約の基準として扱い、作業記録で上書きしない。過去の作業記録と現在の大枠が異なる場合は、その差を確認してから続ける。

現在の会話と依頼内容を中心に、ブランチ情報や作業記録の概要・状態・現在地を合わせて対応する作業を判断する。ブランチ名は手がかりとし、作業を特定する唯一の根拠や必須条件にしない。対象が明らかなら指定を求めず、どの作業を続けるか短く伝えて既存の記録を再利用する。候補を区別できない場合だけユーザーに確認し、日付の新しさだけでは選ばない。

通常は各記録の `status.json` と、`tasks.md` または `work.md` 冒頭の概要から候補を絞り、対象の記録を読む。毎回全記録を読まない。Plugin ルートの `scripts/wip.py list --repo <対象>` で状態の一覧を確認できる。`done` の記録は候補から外し、取り込み先に入っていれば削除できることを伝える。取り込み先に入ったかは `scripts/wip.py sweepable --repo <対象> --base <取り込み先>` で確認できる。

docs/ や特定の Skill の使用履歴がなくても単独で使えるが、作業に必要な目的・制約を依頼や既存資料から確認し、全プロジェクトの大枠を黙って新設しない。

## 記録の保存先と内容

保存先は、対象プロジェクトの共有設定 `.hq/v2/settings.json` の `wip.path` に従う。値はリポジトリのルートからの相対パスで、未指定なら `wip`。値が文字列でない、空、絶対パス、`..` を含むなどの不正な場合は、標準値に戻さず問題を伝える。保存先が Git の管理対象から外れている場合は、記録を作る前に伝える。以下の `wip/` は設定した保存先を指す。

新しい作業は `wip/YYYYMMDD-<作業名>/` に置く。日付は利用者のタイムゾーンでの着手日、作業名は英小文字・数字・ハイフンとする。同名を上書きせず接尾辞で区別する。対応する既存記録があれば再利用し、同じ作業の記録を複製しない。

記録の構成・SOT への影響の判断・要求の書式・状態ファイル・状態の変更・削除の条件は、[作業記録の形式と整理](../../docs/work-records.md) に従う。この Skill では次の手順を担う。

- 着手時に、作業が SOT（docs/）の範囲を変えるかを判断する。変えるなら必ず記録を作る。変えないなら、残す判断・引き継ぎ・合意の必要性から作るかを決める。規模や工数では決めない。
- 記録を作るときは [requirements.md](assets/wip/requirements.md)・[design.md](assets/wip/design.md)・[tasks.md](assets/wip/tasks.md)・[status.json](assets/wip/status.json) の雛形を使う。短い内容は `work.md` にまとめ、要求の4項目（Goal・Context・Constraints・Done When）を先頭に置く。ユーザーの指定と既存構成を優先する。
- 状態を変えたとき、PR を作成したとき、SOT への影響の判断を見直したときは、同じ変更で `status.json` と記録の現在地を更新する。

ユーザー要求、提案、仮定、未決事項、合意済みの判断を区別する。設計判断をユーザー要求として書かない。既存の基準は参照し、対象の作業の具体的な条件・差分を記載する。調査・実験では確かめる問いと終了条件を使い、実験の成功を採用の合意と扱わない。

作業記録はコードや関連文書とともに Git 管理し、変更の経緯は Git history に残す。本文は現在の要求・設計・合意・進捗・次の作業が分かるよう更新する。判断理由や検証結果は残し、変更前の全文や更新履歴を本文へ逐一複製しない。

コミットのタイミングと単位はプロジェクトの規約やユーザーの指示に従い、記録更新ごとの個別コミットは必須にしない。関連するコミットには必要な記録の更新・移動・削除も含める。

## 合意した範囲を実行する

要求・設計・必要なタスクの案をまとめて提示し、合意後に実装・実行する。ファイルごとの承認を標準にせず、タスクリストだけの独立した承認も求めない。依頼や既存記録で得た同じ範囲の合意は引き継ぐ。未決事項は実行前に必要なものと後で決められるものを分ける。

合意の対象範囲・日付・根拠となるユーザーの指示を残す。ファイルの存在、経過時間、無応答を承認と扱わない。相談・記録だけの依頼では、実装や調査の実行へ勝手に進まない。

実行中は意味のある判断・進捗・結果を更新する。変更が必要なら要求・設計・タスクへの影響を揃え、追加の合意は変更した部分に限る。合意範囲内の実装上の選択に形式的な承認を追加しない。

## 大枠を変える必要が出たら

docs/ に記載した主要要求・基本設計・方針・制約を変える場合は、変更案・理由・影響を相談し、合意した内容を該当文書と図表へ反映する。合意まで影響する実行は止めるが、独立して進められる作業は続けてよい。変更を作業記録だけに閉じ込めたり、コードの現状に合わせて大枠を黙って書き換えたりしない。

大枠の中で決められる実装詳細は作業記録と実装・テストに残し、docs/ へ逐一転記しない。広い見直しが必要なら、その相談を実装と区別して扱う。別 Skill の呼び出しを条件にせず、この Skill だけでも必要な変更の相談・反映を進められる。

## 検証と完了

対象の作業の Done When を適切な方法で確認し、プロジェクトの検証・Git・PR 規約に従う。実施した方法・結果・未実施の検証と理由を記録し、タスク完了を条件の充足の代わりにしない。

実装作業は、対象の条件の充足、関連する大枠との整合、必要な docs/ 更新を確認して完了する。相談・設計・記録だけの依頼は、その成果と未決事項が整理できれば完了でき、実装済みであることを要求しない。調査・実験は定めた終了条件と結果で判断する。未完了の条件・未反映事項があれば作業全体を完了扱いしない。

完了したら、継続して必要な仕様・判断を関連文書へ反映し、最終の状態・検証結果を記録して `status.json` を `done` にする。取りやめは利用者の指示や記録で明示された場合だけ `done` にし、理由と未達の条件を残す。完了・取りやめにした変更では記録を削除しない。削除は、その最終記録が取り込み先に入った後の別の変更で、[削除の条件](../../docs/work-records.md#削除) に従って行う。削除の判断と実施には `sweep` Skill を使えるが、その実行は必須にしない。プロジェクト独自の保存方針があれば優先する。

## 中断と再開

中断時は現在地、未決事項、合意待ちの範囲、次の作業を残す。セッションの終了だけでは保留や完了の状態に変えない。

再開を見込む当面の保留は、`status.json` を `paused` にし、理由を記録して `wip/` に残す。削除済みの作業の参照・再開が必要な場合は、[削除した記録の参照](../../docs/work-records.md#削除した記録の参照) の方法で Git の履歴から確認し、再開するなら `wip/` に復元する。

再開時は関連する記録・docs/・実装の変化を確認し、古い記録を更新して続ける。合意や完了済みの作業を形式的にやり直さない。

明示的なユーザー指示を優先する。この Skill の使用だけで公開・デプロイ・外部への送信を許可されたと扱わない。
