# 変更をレビューできる PR にまとめる

差分全体の目的・変更後の挙動・検証結果を、会話を読んでいないレビュアーが判断できる形にまとめる。git・release・steering の使用履歴を前提にせず単独で使える。下書き、作成、更新のうち依頼された段階だけを実行し、PR の依頼を実装変更・merge・公開の許可とは扱わない。

## 対象と材料を確認する

CWD から Git のルートを取得し、利用先の指示、現在のブランチ・未コミット変更、remote、関連する既存 PR を確認する。`.hq/v2/references/gotchas.md` や同等の記録があれば、今回に関連する項目を参照する。

対象リポジトリと base/head を確定する。通常作業用の既定ベースと、リリース PR の取り込み先を混同しない。既存 PR の更新では現在の取り込み先を確認し、設定の既定値だけで変更しない。不明で差分や取り込み先が変わる場合だけ確認する。

対象ブランチと base の比較から PR 全体の差分を読み、実際に含まれる変更・検証結果を確認する。最後のコミットや会話中の予定だけで本文を書かない。未コミット・未 push の変更と、GitHub 上の PR が含む変更を区別する。必要な検証は利用先の Git・リリース規約に従い、未実施・失敗を成功扱いしない。

## 指示と書式を選ぶ

利用先ルートの `.hq/v2/pr.md` が存在すれば、必ず読み、その PR 固有の指示・タイトル規約・本文書式に従う。ファイル名は Plugin の配置ではなく、操作対象プロジェクトを基準に解決する。参照先や関連ディレクトリの指示が指定されていれば、必要な範囲を確認する。

今回の明示的なユーザー指示を優先し、その範囲で利用先の規約を適用する。`.hq/v2/pr.md` が書式を指定していれば、標準見出しを追加したり、標準書式へ変換したりしない。指示だけで本文書式が指定されていない場合は、既存のプロジェクトの PR テンプレート、それもなければ [標準本文](assets/pr-body.md) で未指定部分を補う。複数のテンプレートは指定や変更内容から選び、区別できない場合だけ確認する。

`.hq/v2/pr.md` がない場合も、既存の PR テンプレートやプロジェクト固有の書式を尊重する。独自書式がなければ標準本文を使う。指示ファイルの新設を PR 作成の条件にせず、勝手に利用先の規約を作らない。

## タイトルと本文を書く

タイトルは変更の目的・結果が分かる簡潔な一行とし、利用先の規約がなければ Conventional Commits の `<type>: <description>` を標準とする。ブランチ名や識別子だけで内容を指し示さない。

本文は現在の差分に合わせて書き直す。標準書式では、解決する問題と変更後の挙動、主な変更、検証の方法・結果を短く示す。判断に必要な前提はその場に添え、必要な場合にだけ具体例・互換性・移行・残る制約を説明する。経緯やファイル一覧を無条件に列挙しない。

各項目の説明と根拠は、選んだ書式の中へ収める。実施していない検証をチェック済みにせず、不明点は不明と記す。仮説を確認済みの不具合として書かず、テンプレートの説明文・記入例・不要な空見出しを完成本文へ残さない。人間の判断が必要なら、決める事項・選択による違い・推奨と理由を示す。必要でなければ判断待ちの項目を作らない。

## 作成・更新して確認する

GitHub へ書き込む前に、同じ作業の既存 PR を確認して重複を避ける。既存の人手の追記・レビュー上必要な情報は保持し、現在の差分と食い違う記述は修正する。本文だけの依頼では作成・更新・push を実行しない。

ドラフト指定や実際の未完了事項があれば Draft とし、それ以外は通常のレビュー可能な PR とする。単に人間の確認を待つためだけにドラフトへ固定しない。必須検証が失敗・未実施なら、その事実と不足を明示し、準備済みとは扱わない。Draft は検証や権限を省略する理由にはしない。

書式や改行を保持できる方法で本文を渡し、シェルへ本文を直接展開してコマンドとして解釈させない。依頼の範囲で作成・更新した後、URL、base/head、タイトル・本文・Draft 状態が意図どおり反映されたか確認する。PR の作成・更新と取り込みは別の段階として報告する。
