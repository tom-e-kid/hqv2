# HQ の作業メモを点検・整理する

HQ checkout の作業記録（`.hq/v2/settings.json` の `wip.path`、未指定は `wip/`。以下 `wip/`）を点検する。手動でも定期実行でも同じ判断基準を使う。Plugin 利用先の巡回、既存の worktree・作業ブランチの削除、Issue のクローズ、自動マージは行わない。定期タスクからの実行依頼は、この範囲の編集・コミット・push・PR 作成と更新の許可として扱う。読み取り確認だけの依頼では変更しない。

## 開始と重複防止

1. CWD の Git ルート・origin が HQ (`tom-e-kid/hqv2`) であることを確認する。[AGENTS.md](../../../AGENTS.md)、[Git 規約](../../../.hq/v2/git.md)、[設定](../../../.hq/v2/settings.json) を読む。Gotchas の記録（`.hq/v2/settings.json` の `gotchas.path`、未指定は `GOTCHAS.md`）または同等の記録があれば関連項目を参照する。
2. `git worktree list --porcelain`、ブランチ、未コミット変更、進行中の Git 操作と、develop 向けの open PR を確認する。既存の作業メモ整理 PR は head 名だけでなく目的・差分でも照合する。人間が閉じた未マージ PR を自動で再作成せず、その理由を確認する。
3. 同一の点検が並行して走らないよう、基準 checkout の `.hq/v2/.ignore/work-maintenance/lock/` を原子的なディレクトリ作成で取得する。保持者と開始時刻を記録し、終了時に自分のロックだけ解放する。既存ロックは奪わず今回を見送る。中断後に残ったロックは保持者の終了を確認するまで削除しない。
4. origin を fetch し、最新の `origin/develop` を評価の基準にする。主 checkout のブランチ切り替え・pull・stash は行わない。変更が必要になったら、AGENTS.md の指定配置に develop 系列から専用ブランチ・worktree を準備する。既存の整理 PR があれば対応するブランチ・worktree を再利用する。

API・認証・fetch の失敗を「変更なし」と扱わない。確認できない根拠に依存する整理は保留する。別作業や人間の未コミット変更・進行中操作がある checkout は編集せず、強制更新・force-push で解消しない。

## 評価する観点

最初に `wip/` の各記録の概要と状態を確認し、関連する要求・設計・タスクを読む。

作業ごとに以下を照合する。

- **状態と根拠**: 関連 PR の base/head・merge の有無、Issue の状態、develop に入った変更を記録と比較する。PR が複数ある作業では一件の merge だけで全体完了としない。API の close と merge を区別し、Issue が閉じているだけで受け入れ条件充足としない。
- **終了条件と残作業**: 要求・受け入れ条件、未決事項、未反映事項、検証結果を読む。マージやチェックボックス、経過日数だけでは完了にしない。実機確認待ちを実施済みに書き換えず、今回の完了条件外か作業全体の残件かを記録に基づいて区別する。
- **継続・保留・取りやめ**: 近いうちに再開する予定か、明示された保留・取りやめかを確認する。更新が古いだけで取りやめや長期保留を推測しない。後続へ引き継いだ場合は引き継ぎ先・残件の所有先を確認する。
- **継続して必要な知識**: 現行仕様・運用・制約・判断のうち、作業メモだけにある内容を特定する。既存の正式文書と照合し、既に合意され根拠がある内容だけを適切な関連文書へ反映する。新しい仕様や方針の判断は行わず、必要なら確認事項として残す。
- **参照とリンク**: 現行文書からの参照、今後も必要な設計判断・検証根拠・再開情報を確認する。完了後も必要な内容は記録を残さず関連文書へ反映し、記録へのリンクは反映先かコミットを固定した URL に付け替える。
- **他作業との競合**: 関連ブランチ・worktree や open PR に進行中の更新がないか確認する。活動中・未コミット変更あり・使用状況不明の記録は今回の編集対象から外す。他作業を終了扱いにしたり残件を肩代わりして実装したりしない。

## 分類と変更

[wip の完了・中断方針](../../../skills/wip/SKILL.md) に沿って分類する。

| 分類 | 条件と実施内容 |
| --- | --- |
| 維持 | 継続中、再開を見込む保留、必要な検証・判断が未完了、または根拠不足。確認済みの進捗が古ければ、競合しない範囲で状態・残件・次の行動だけ更新する。保留は状態と理由を記録し、完了に変えない。 |
| 削除 | 完了・取りやめを根拠で確認でき、必要な知識の反映とリンクの付け替えが済んでいる。最終状態・理由・検証結果を含む全文を先にコミットしてから削除する。 |

削除は wip の削除条件に従い、最終記録が develop の履歴に残る場合に限る。最終記録が既に develop にある記録は削除できる。今回の PR で最終状態を記録する場合は、リポジトリの設定で取り込み方法がマージコミット・rebase に限られていなければ、その PR では削除せず完了（取り込み後に削除）として残し、取り込み後の点検で削除する。削除する PR の本文には、最終記録を含むコミットへのリンクを残す。

削除する記録へのリンクは、反映先かコミットを固定した URL に付け替え、付け替えずに取り除かない。未採用案・過去の判断を現在の合意や実装済みの事実へ書き換えない。

確認日だけの更新、文章の好みだけの整形、全記録への定型文追加は行わない。変更がない点検のために毎回新しい作業メモを作らない。対象・分類・根拠・見送り理由は PR 本文または実行結果で追えるようにする。

## 検証して PR にする

1. 編集直前と push 前に対象の最新状態を再確認する。origin/develop、関連 PR、対象ファイルが評価後に変わっていたら、該当する判断・差分を見直す。並行更新が不明ならその対象を保留する。
2. 差分を作業メモ、必要な知識の反映先、関連リンクの修正に限定する。整理のために製品コード・配布設定を変更しない。
3. Git 規約と [検証手順](../../../docs/validation.md) の必須チェックを実行する。付け替えたリンク、削除前の最終記録のコミット、意図しない削除がないことも確認する。失敗時は commit・push を止め、変更と失敗理由を保持して報告する。
4. [PR 手順](../../../skills/pr/SKILL.md) に従い、検証済みの変更を commit・push し、develop 向け通常 PR を作成・更新する。作成直前にも既存 PR を確認する。本文は問題と変更後の状態、作業ごとの分類理由・根拠へのリンク、検証結果、未確認事項を示す。人間の追記やレビューの文脈を保持する。
5. PR の URL・base/head・本文を確認する。自動マージやレビュー返信・Resolve はこの整理依頼に含めない。次回の再利用に必要な作業ブランチ・worktree を保持する。

## 無変更時と通知

ローカルの実行状態を基準 checkout の `.hq/v2/.ignore/work-maintenance/state.json` に保存する。前回確認した develop のコミット、整理 PR、通知済み確認事項とその根拠を記録し、次回は現在の事実を再確認する。状態ファイル自体は Git に含めない。

通知は PR の作成・実質的な更新、新しい確認事項、実行失敗、復旧時に行う。変更も新しい確認事項もなければ通知しない。未解決事項や同じ失敗を毎週繰り返し通知せず、根拠・状況が変わった場合に更新する。初回で比較情報がなければ `wip/` の全記録を評価する。実行できなかった点検を成功として記録しない。
