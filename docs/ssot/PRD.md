# HQ Plugin の目的と要求

状態: 叩き台。文書構成は合意済み。内容は既存方針を整理した草案であり、全体の合意・実プロジェクトでの動作確認は未完了。

## 目的

HQ は、SDDの考え方を活かし、SSOTを判断基準にした開発を支援する、Codex・Claude Code 向けの Plugin である。

目的・要求・制約についての合意を SSOT に残し、それを基準に作業を具体化して実装・検証する。開発を通じて方針が変わる場合は、その判断を SSOT に反映し、後の作業でも基準として使える状態を保つ。

セッションを跨いでも判断の根拠を追えること、確認済みの事実と未確認事項を区別できること、利用先の規約と人間の判断を尊重することを重視する。

## 用語

用語の定義・表記は [用語集](GLOSSARY.md) に従う。

## 利用者と課題

主な利用者は、Codex または Claude Code と協働してソフトウェアを開発・保守する開発者。HQ 自体の保守担当も、利用先での検証と配布を行う。

解決する課題は次のとおり。

- 目的や主要要求が曖昧なまま実装が進み、個別作業の判断がぶれる。
- 合意・判断理由・未完了事項が会話に埋もれ、再開時に確認をやり直す。
- 作業記録の状態と実態がずれ、完了記録が残り続ける、または必要な記録を失う。
- Git・PR・リリースの確認漏れや、過去に遭遇した問題が繰り返される。
- 利用するツールや利用先プロジェクトの違いを無視した自動化が、未確認事項を成功扱いしたり、意図しない変更を行ったりする。

## 提供範囲

HQ は、SSOT を用いた開発・保守を継続できるよう、次の活動を支援する。

- 目的・要求・制約を明らかにし、合意した方針を SSOT に残す。
- SSOT を基準に作業を具体化し、合意から実行・検証・成果の取り込みや公開までを進める。
- 作業を通じて得た知見や変更の必要性を踏まえて SSOT を見直し、合意した方針と実装の整合を保つ。
- 作業の根拠・現在地・知見を残し、セッションや担当が変わっても継続・再利用できるようにする。
- 確認漏れや意図しない操作を抑え、品質と安全性を確かめる機会を設ける。

利用者は必要な支援を個別に選べる。すべての支援を順番に利用することや、特定の開発フローを全面採用することを前提にしない。

具体的な機能・操作・設定は [README](../../README.md)、各 Skill とその参照資料で管理する。

## 守るべき要求と制約

以下は既存の開発規約・Skill・共通資料から整理した判断基準の草案。実装済み・検証済みの宣言ではない。

### R1: 利用先プロジェクトと利用するツールを尊重する

- 共通 Skill は Codex・Claude Code で利用でき、特定のツール名・モデル・agent・Hook を前提にしない。
- 利用先の指示・設定・既存の同等文書を尊重する。不正な設定を黙って既定値へ戻さない。
- Codex または Claude Code に固有の機能は対象と役割を明示し、それぞれのツールで検証する。片方での成功をもう片方の確認済みと扱わない。

### R2: 合意を経て作業する

- プロジェクト全体の大枠と、一つの作業の詳細を分ける。要求・設計をまとめて合意してから実装へ進む。
- 既存の合意は引き継ぎ、セッション開始を理由に同じ範囲の承認を求め直さない。未合意の案を現在の方針として扱わない。
- 相談・仕様策定・下書きなど、依頼された段階を超えて実装・公開へ進まない。

### R3: 判断基準と作業の根拠を維持する

- SSOT の対象は利用先の登録で定める。配置だけで推測せず、SSOT のないプロジェクトでも必要な作業を進められる。
- 作業を方向付ける要求・責務・境界・制約への影響を確認し、合意した変更は SSOT へ反映する。全実装詳細は転記しない。
- 作業記録には取り込みまでに確認できる完了条件と現在地を残す。同じ作業はセッションを跨いでも再利用する。最後の PR の中で取り込み前に `done` にし、取り込み後の運用確認は検証資料・チェックリストで別に管理する。
- 完了や削除は状態・内容・取り込み先などの根拠で判断し、PR の取り込みや経過日数だけで断定しない。継続して必要な知識と最終記録の履歴を保持する。
- Gotchas は利用先の共有記録として扱い、プロジェクト固有の知見を Plugin 自体に蓄積しない。

### R4: 人間の判断と機械処理を分ける

- 機械処理は、対象の特定・設定・コミット・変更の有無など、明示した条件から再現可能な事実を取得する。
- 要求・設計・実装の意味上の整合性と、変更の必要性は、文脈と根拠を踏まえてエージェントが判断する。
- 注意が出ないことを整合性の確認済みと扱わず、取得失敗・対象不明・未確認を問題なしと区別する。PR 作成前に作業記録の確認が必要な場合は呼び出しを一旦止め、エージェントが最後の PR かを判断・対応して再実行する。中間 PR の未完了状態を機械的に不正としない。

### R5: 利用者のデータと操作権限を守る

- 他の作業の変更、既存 Hook、設定、公開済み成果物を意図せず上書き・破棄しない。
- Plugin の導入だけで Git Hook の導入や AI レビューへの自動対応を有効化しない。変更・push・返信・Resolve 等は利用先の許可とホストの権限の範囲で行う。
- 自動処理には終了条件・上限・中断と再開の扱いを持たせ、期限到達や処理の取り残しを成功と扱わない。
- 安全性を確認する機能は、何をどこまで確認するかを利用者が把握できるようにする。

### R6: 配布と検証の根拠を示す

- 名前・バージョン・配布設定は Codex・Claude Code で整合させる。利用者に影響する変更を CHANGELOG に残す。
- 構造検証・自動テスト・Codex・Claude Code での動作確認・実プロジェクトでの確認を区別する。
- 実プロジェクトで確認すべき項目を [検証チェックリスト](validation-checklist.md) に残す。未実施・失敗・対象外を合格と扱わず、利用したツール・検証対象・根拠を記録する。

## 対象外

- Codex・Claude Code 自体の実行基盤、権限管理、標準の開発機能の再実装。
- 全プロジェクトへの同一の技術スタック・文書構成・Git 運用の強制。
- すべての意味上の判断の機械判定、または不具合・秘密情報流出を完全に防ぐ保証。
- 個別作業の全タスク・実装詳細・実行履歴を、この PRD に集約すること。

## 成功の判断

利用先で、SSOT が個別作業の判断と検証に使われ、開発を通じた方針の変更が反映されることを成功の基準とする。そのうえで、作業の合意、実装・検証、再開・整理、取り込みまで、依頼された範囲を根拠付きで遂行できることを確認する。

確認には [検証チェックリスト](validation-checklist.md) を用いる。構造検証の成功だけでは達成としない。公開判定に必須とするケースと、利用するツール・利用先プロジェクトの組み合わせは未決であり、すべてのケースが合格済みとは扱わない。

## 文書の責務

- `docs/ssot/`: HQ 自身の PRD・用語集・実プロジェクト検証チェックリストを置く。要求と重要な境界・制約は PRD、用語の定義・表記は用語集を正本とし、FDS・ADD は作成しない。
- `docs/references/`: 複数 Skill や Hook・スクリプトにまたがる、利用時の共通規則・利用ガイドを置く。
- `skills/<name>/references/`: その Skill に属する参照資料を置く。他の Skill から参照されることだけを理由に共有資料へ移さない。
- `docs/validation.md`: HQ 自体の開発用検証手順。取り込み先での確認項目はチェックリストを参照する。
- 作業記録・実装・テスト: 作業の要求・設計・進捗、詳細な動作と検証を保持する。

この構成は HQ 自身に適用する。配布する sdd Skill の既定の文書構成や、利用先の構成を変更する判断ではない。

## 未決事項

- 上記の目的・利用者・要求・対象外に、追加または修正すべき点があるか。草案全体の合意は今後の相談で行う。

- 成功を継続的に評価するための測定方法・定量的な達成基準が必要か。

Codex・Claude Code の対応バージョン・個別機能の詳細・操作方法は、実装と利用ガイド、必要な作業の具体化で扱う。
