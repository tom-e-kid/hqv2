# HQ Plugin の検証

この文書は Plugin 自体を開発・保守するための検証手順です。実行する段階と必須条件は [Git 規約](../.hq/v2/git.md) に従います。すべてのコマンドはリポジトリのルートで実行します。

## 構造・参照と配布設定

Python 3.10 以上と、配布設定を確認する対象製品の CLI を用意します。`scripts/validate.py` は Python 標準ライブラリだけで実行でき、PyYAML は不要です。

通常の構造・参照のチェックは以下です。

```bash
python3 scripts/validate.py
claude plugin validate .
claude plugin validate .claude-plugin/plugin.json
```

Claude Code はルートの `CLAUDE.md` がインストール先のプロジェクトコンテキストとして読み込まれない旨を警告します。このファイルは Plugin 自体の開発用なので、この警告は想定内です。それ以外の警告・エラーは内容を確認して解消してください。`--strict` を付けると、この想定内の警告もエラーになり検証に失敗します。

個人の設定を変更せず、Codex でカタログが読み込めることを確認できます。

```bash
codex -c "marketplaces.hq-marketplace.source=\"$(pwd)\"" \
  -c 'marketplaces.hq-marketplace.source_type="local"' \
  plugin list --marketplace hq-marketplace --available --json
```

JSON に `hq@hq-marketplace` が出ることを確認します。

## リリース準備の検証

リリース準備を確定する場合は、追加で次を実行します。

```bash
python3 scripts/validate.py --release
```

両マニフェストと設定の整合、対象バージョンの日付付き CHANGELOG を確認します。まだ `Unreleased` のみの開発中は、このチェックが失敗するのが意図した動作です。この検証だけで公開済みとは判断しません。

## Skill の専用検証と PyYAML

`scripts/validate.py` は、マニフェスト・カタログ・必須リソース・設定・Markdown のローカル参照と、各 Skill の frontmatter の名前・説明の基本形式を確認します。frontmatter 全体を YAML として解析するものではありません。成功しても YAML 全体の構文や他のフィールドの妥当性まで確認済みとは扱いません。

Skill を追加・変更する際、Codex の skill-creator が利用できる環境では、付属の `scripts/quick_validate.py` で追加確認できます。この外部ツールは HQ には同梱していません。配置を確認し、`skill_validator` に実際のパスを指定します。以下は標準的な配置の例です。

```bash
skill_validator="${CODEX_HOME:-$HOME/.codex}/skills/.system/skill-creator/scripts/quick_validate.py"
test -f "$skill_validator"
```

専用検証ツールは PyYAML に依存します。`ModuleNotFoundError: No module named 'yaml'` が出た場合は検証が起動しておらず、Skill の検証成功を意味しません。システムの Python を変更せず、一時仮想環境に依存を導入し、その環境の Python で実行します。以下は過去の検証で使用した PyYAML 6.0.3 を指定した例です。パッケージ取得にはネットワーク接続が必要です。

```bash
validation_env="$(mktemp -d "${TMPDIR:-/tmp}/hq-validation.XXXXXX")"
python3 -m venv "$validation_env"
"$validation_env/bin/python" -m pip install 'PyYAML==6.0.3'
for skill in skills/*/; do
  "$validation_env/bin/python" "$skill_validator" "$skill" || exit 1
done
```

各コマンドの成功を確認してから次へ進み、全 Skill が `Skill is valid!`・終了コード 0 となることを確認します。ツールや依存がなく実行できなかった場合は、その理由と未実施の範囲を記録します。PyYAML はこの専用検証ツールの依存であり、HQ Plugin の実行時依存ではありません。Plugin の利用者に導入を要求しません。

## 検証スクリプトの構成と実行時間

現時点では `scripts/validate.py` を共通検証の入口として維持します。検証項目の増加により実行時間が開発や CI の支障になった場合は、まず検証単位の所要時間を計測し、時間のかかる処理を特定します。そのうえで、処理間の依存関係と共有ファイルへの書き込みの有無を確認し、独立した検証の並列実行を検討します。

ファイル分割だけでは並列実行にはなりません。保守性のための関数・モジュール分割と、実行時間を短縮するための並列化を分けて判断します。並列化する場合も、全検証の結果を集約し、一つでも失敗したら全体が失敗する挙動を維持します。プロセス起動などの負荷も含めて効果を計測してから採用します。

## モデルによる動作確認

カタログの読み込みと Skill の構造検証は、モデルが手順に従って作業することの保証ではありません。
配布前には新しいセッションで次のケースを確認します。

| ケース | 確認すること |
| --- | --- |
| sdd で大枠だけ相談 | 詳細を先回りして確定せず、実装へ進まず、合意状態と未決事項を残す |
| steering で未合意の機能追加 | 大枠を参照し、作業の要求・設計をまとめて相談してから実装する |
| 大枠の中の実装詳細 | 作業記録と実装・テストへ残し、docs/ に逐一転記しない |
| 大枠を変える作業 | 変更を相談・合意し、該当する docs/ と図表を更新する |
| steering だけの調査・実験 | sdd や docs/ を必須にせず、問いと終了条件を記録する |
| セッションを跨ぐ再開 | 同じ作業記録を使い、大枠・実装の変化を確認し、合意を求め直さない |
| 対象が明らかな作業の継続 | 会話と依頼内容から既存記録を選び、ブランチ名との一致や毎回の指定を必須にしない |
| 複数の active と多数の archived | active の概要・状態で候補を絞り、必要な記録だけ読む。候補を区別できない場合だけ確認する |
| 保留と archived からの再開 | 状態・理由を残し、セッション終了だけでは移動しない。再開は同じ記録を使い、移動で参照を壊さない |
| 完了・取りやめの記録整理 | 継続して必要な内容を反映し、最終記録のコミットを確認してから削除する。削除とリンク整理もコミットし、継続参照が必要な記録は保持できる |
| 旧配置の作業記録 | 既存記録を使い、一律の移行や重複作成をしない |
| 作業記録の Git 管理 | 本文から現在地を把握でき、判断理由・結果を残す。変更前の全文は Git history に任せ、関連するコミットに記録の更新・移動・削除も含める |
| 相談・設計だけの完了 | 実装済みを完了条件にしない |
| 1ファイルの作業記録 | 要求・設計・タスクと合意状態を混同しない |
| 明確で軽微な修正 | 一律の文書作成を要求せず、プロジェクトの規約に従う |
| 非 JavaScript のプロジェクト | package.json や特定のフレームワークを前提にしない |
| gotchas だけで記録 | 他の Skill を必須にせず、対象プロジェクトに発生条件・問題・対処・確認状況を残す |
| 類似問題の参照 | 症状だけで同じ原因と決めず、記録の適用条件を照合する。記録がなくても空ファイルを作らない |
| 未確認の原因・対処 | 仮説と確認済みの事実を区別し、記録の完了を問題の解消と扱わない |
| 重複・古い回避策の整理 | 根拠を確認して更新し、正式な手順や標準メモリと全文を二重管理しない |
| steering なしの Git 作業 | 作業記録を一律に作らず、依頼された段階だけを進める |
| 既定ベースを変えた後の再開 | 作業開始時の取り込み先と既存 PR を照合し、黙って変更しない |
| worktree の新設と既存環境 | 名前から実体を判定せず、名前の衝突やローカル設定の引き継ぎを確認する |
| 必須検証の失敗・未設定 | コマンドを捏造せず、未実施を成功扱いして先へ進まない |
| PR を省略する取り込み | 許可条件・理由を確認し、作業ブランチと必須検証を維持する |
| 初回のリリース準備 | 未公開の予定バージョンを自動で上げず、対象・初回番号・CHANGELOG を確認する |
| 開発と公開のブランチが異なる | 準備の更新を開発側に残し、リリース PR の取り込み先を公開ブランチにする |
| 公開途中の失敗・同名タグ | 反映済みの段階を確認して再開し、既存タグ・公開済みバージョンを上書きしない |
| 独自 PR 書式なしの下書き | 標準本文で差分全体と検証を説明し、作成・push は行わない |
| `.hq/v2/pr.md` がある PR | 指示・独自見出しに従い、標準書式の見出しを追加しない |
| PR 指示だけがあり、既存テンプレートもある | 指示を守り、未指定の書式は既存テンプレートで補う |
| Skill ごとの旧 Gotchas | 既存の保存先を尊重し、無断の移動・統合・重複作成をしない |

## PR フィードバック対応

`python3 -m unittest discover -s tests -v` で、待機・ページ分割・複数レビュアー・失敗・排他・再開・上限・Hook 入出力を確認します。[運用手順](pr-feedback.md) に沿って対象製品の新しいセッションで PR 作成後の登録、Stop による待機・継続、返信・Resolve、修正後の再確認、Cap と終了報告を検証します。API を差し替えたテストやマニフェスト検証だけで製品内の動作を確認済みとしません。Codex の Interrupt と両製品の SessionEnd も対象です。
