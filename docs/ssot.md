# SSOT と PR 作成時の確認

sdd・wip・pr・git と判定スクリプトが共有する、SSOT の定義・登録・影響の判断と、PR 作成時に SSOT の確認漏れを伝える仕組みです。

## SSOT

この Plugin では、SDD で作成・維持する PRD・FDS・ADD 等の文書を SSOT（Single Source of Truth、正本）と呼びます。要求・仕様・設計について、合意事項と検討中の事項を記録し、個別作業の判断の基準とします。

SSOT は、すべての情報を一つのファイルに集めることではありません。要求は PRD、基本設計は ADD のように、文書の分担で成り立ちます。手作業で編集した文書や、引き継いだ既存の同等文書も含みます。

SSOT の有無と対象文書は、プロジェクトごとに定めます。SSOT のないプロジェクトもあり、SSOT や sdd の利用は必須ではありません。AGENTS.md などの指示ファイルは、自動的には SSOT に含めません。

## 登録

SSOT は、共有設定 `.hq/v2/settings.json` の `ssot.paths` に、リポジトリのルートからの相対パス（ファイルまたはディレクトリ）で登録します。保存場所やファイル名からは推測しません。

```json
{ "ssot": { "paths": ["docs"] } }
```

- 未指定なら SSOT は未定義です。PR 作成時の確認は適用しません。
- 通常は、sdd が文書を置く `sdd.path`（未指定は `docs`）を登録します。既存の同等文書を引き継ぐ場合は、その場所を登録します。
- 登録は「この文書を SSOT として使う」という宣言です。内容の合意を判定するものではありません。SSOT は育てていくもので、草案や検討中の事項も SSOT に含まれます。
- `.`・絶対パス・`..` を含むパスは使えません。リポジトリのルートを登録すると、実装まで SSOT になるためです。

## SSOT への影響

作業記録の `ssotImpact` は、作業が次の事項に影響する可能性があるかの判断です。

> 対象ユーザー・提供価値・主要な振る舞い・外部との契約・責務や境界・技術方針・制約など、個別の実装判断を方向付ける事項。

変更の規模や工数では判断しません。影響する可能性がある作業は、SSOT が未定義のプロジェクトでも作業記録を作ります（[作業記録の形式と整理](work-records.md#ssot-への影響)）。

## PR 作成時の確認

目的は、SSOT を見直す機会の抜けを注意することです。SSOT と実装の意味の整合性は判定しません。

次をすべて満たす PR に、注意を1件出します。

- SSOT が登録され、PR の head のコミットに存在する。
- 変更に含まれる作業記録に、`ssotImpact: true` がある。
- 実装（作業記録と SSOT 以外）の変更があり、SSOT の変更がない。

注意（`ssot-review`）は、該当する記録を挙げ、SSOT の確認・更新が必要か確かめるよう求めます。既存の記述で足りる、以前の PR で更新済み、まだ判断を変えない、という結論でも構いません。SSOT の中の合意済み・検討中の区別は判定せず、注意を受けたエージェントが内容を読んで判断します。

### 確認の限界

- 注意が出ないことは、SSOT と実装の整合を確認できたことを意味しません。SSOT に変更がある PR も、条件に当てはまらないだけです。
- PR が記録を触ったことは、その記録の作業がこの PR で SSOT に関わる変更をしたことを意味しません。注意は記録の判断の誤りを断定しません。
- 実装の変更は、作業記録と SSOT 以外のすべての変更を指します。README やテストだけの変更でも条件に当てはまることがあります。
- 作業記録を変更に含まない作業は判定できません。

### 判定できない理由

注意とは分けて伝えます。

| 理由 | 状況 | 対応 |
| --- | --- | --- |
| `invalid-status` | 変更に含まれる記録の状態ファイルが欠けている、または不正 | 状態ファイルを直す |
| `ssot-missing` | 登録した SSOT のパスが head のコミットに存在しない。すべて存在しなければ判定しない | 登録か文書を直す |

設定（`ssot.paths`・`wip.path`）が不正な場合も、判定できないことを伝えます。

### 判定の仕組み

Plugin ルートの `scripts/wip.py check-pr --repo <対象> --base <取り込み先> [--head <コミット>]` が判定します。対象は、取り込み先との分岐点から head（省略時は HEAD）までのコミット済みの変更です。設定と状態ファイルも head のコミットから読み、未コミットの変更は含めません。記録のディレクトリごと削除した変更は、その記録を判定から外します。PR 作成は止めません。

PR を作る前の確認は、pr・git・wip の手順で行います。Codex・Claude Code の Plugin Hook（`PostToolUse`）は、エージェントが `gh pr create` や PR 作成用の MCP ツールで PR を作った後に、作成された PR へ同じ判定を行い、確認漏れを補います。

Hook は、PR を作るコマンドを解析せず、作成された PR を根拠にします。ツールの実行結果から PR の URL を一つ特定し、`gh pr view` で GitHub 上の head・base のコミットを取得して、そのコミットを判定します。作業中の checkout・ブランチと未コミットの変更は判定に含めません。worktree はコミットを共有するため、どの worktree から作った PR も判定できます。

次の場合は判定せず、未確認であることを伝えます。問題なしとは扱いません。

- 実行結果から PR を一つに特定できない。
- 作業中のリポジトリに、PR のリポジトリ（owner/repo）を指すリモートがない。同じコミットを持つ別のリポジトリでは判定しない。
- `gh` で PR を取得できない（未導入・認証・通信の失敗、タイムアウト）。
- 作業中のディレクトリが Git リポジトリではない。
- head・base のコミットが手元にない。取得してから `check-pr` の `--base`・`--head` に指定して確認する。

何も出さないのは、PR の head のコミットで SSOT が未定義の場合と、注意の条件に当てはまらず判定できない理由もない場合です。作業中の checkout の状態は根拠にしません。
