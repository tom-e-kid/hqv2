# 作業記録の形式と整理

wip・sweep・pr・git が共有する、作業記録の形式・状態・削除の条件です。SSOT の定義と PR 作成時の確認は [SSOT と PR 作成時の確認](ssot.md) にあります。各 Skill はこれらの規則に従い、自分の手順だけを持ちます。

## 保存先と構成

作業記録は、利用先の共有設定 `.hq/v2/settings.json` の `wip.path`（未指定は `wip`）に置きます。以下の `wip/` は設定した保存先を指します。

```text
wip/YYYYMMDD-<作業名>/
  status.json        状態・SSOT への影響・PR 番号
  requirements.md    要求（Goal・Context・Constraints・Done When）
  design.md          実現方法・判断理由・SSOT への影響・検証方針
  tasks.md           作業と状態、合意の根拠、検証結果、現在地
```

短い内容は `requirements.md`・`design.md`・`tasks.md` を `work.md` 1つにまとめられます。その場合も要求の4項目を先頭に置きます。雛形は wip Skill の `assets/wip/` にあります。

`wip/` には進行中と、再開を見込む保留中の作業を置きます。完了・取りやめた記録は、削除の条件を満たすまでの間だけ残ります。

## SSOT への影響

着手時に、作業が SSOT への影響を持つか、つまり [SSOT への影響](ssot.md#ssot-への影響) の事項に影響する可能性があるかを判断し、作業記録を作るかを決めます。SSOT が未定義のプロジェクトでも同じように判断します。作業の規模や工数では決めません。

| SSOT への影響 | 作業記録 |
| --- | --- |
| あり | 必ず作る |
| なし | 残す判断・引き継ぎ・合意の必要性から判断する。作らない場合も、対応する既存の記録があれば必要な範囲だけ更新する |

判断は作業中に見直してよく、変えた理由を記録に残します。影響なしとして始めた作業が影響を持つと分かったら、記録を作るか、既存の記録の判断を「あり」に改めます。

## 要求の書式

- **Goal**: 何を変えたい・作りたいか。対象範囲と対象外。
- **Context**: 影響する範囲。関係するファイル・ディレクトリ・文書・エラーと、関連する SSOT の箇所。
- **Constraints**: 守るべき標準・アーキテクチャ・要件・規約。
- **Done When**: 何が満たされたら完了とするか。テストが通る、振る舞いが変わる、不具合が再現しないなど、確かめられる条件と確認方法。

Done When は、取り込みまでに確認できる条件で書きます。取り込み後の運用・実環境でしか確認できない事項は、既存の検証資料やチェックリストで別に管理し、参照先を記録します。取り込み自体で満たされる条件だけは、最後の PR を取り込むことを前提に取り込み前に扱えます。必須の検証やレビューが未実施・失敗であることを、この例外で充足済みにしてはいけません。

Done When は完了を判断する根拠です。Done When のない記録は完了を判断できません。

## 状態ファイル

```json
{ "status": "active", "ssotImpact": true, "prs": [123] }
```

- `status`: `active`（進行中）・`paused`（再開を見込む保留）・`done`（完了または取りやめ）。
- `ssotImpact`: SSOT への影響の判断（`true` または `false`）。
- `prs`: この作業の PR 番号。

状態を変えたら同じ変更で `status.json` を更新します。`tasks.md` または `work.md` 冒頭の概要・状態は詳しい現在地を示し、`status.json` と矛盾させません。

PR を作成した手順（wip・pr・git のいずれでも）は、その作業に対応する既存の記録があれば `prs` に番号を追記し、PR のブランチにコミットします。対応する記録がない場合に、PR 番号のためだけに記録を作りません。

## 状態の変更

| 変更 | 条件 |
| --- | --- |
| `active` と `paused` の切り替え | 再開の見込み・保留の理由を記録に残す。セッションの終了だけでは変えない |
| `done`（完了） | Done When の各条件を記録・検証結果などで確認し、作業の最後の PR の中で取り込み前に設定する。取り込み自体で満たされる条件はその取り込みを前提に扱う |
| `done`（取りやめ） | 記録または利用者の指示で、取りやめが明示されている。理由と未達の条件を記録に残す |
| 変えない | 上記を根拠で確認できない。PR がすべて取り込まれた、Issue が閉じた、更新が古いといった事実だけでは変えず、確認事項として伝える |

複数 PR の作業では、タスク・残作業から最後の PR かを判断し、中間 PR は `active` または `paused` のままにします。PR 作成前に確認し、最後なら最終記録を同じ PR に含めます。作成後に漏れへ気づいた場合も、取り込み前にその PR へ追加します。`done` の設定後に同じ目的の達成に必要な残作業が見つかれば `active` へ戻し、完了を装うために別作業へ移しません。独立した追加要求は別作業にできます。

PR を使わない作業も、依頼された成果と完了条件を根拠で確認して `done` にします。PR の新設を完了の条件にはしません。Plugin Hook を使う場合の停止と再実行は [PR 作成前の作業記録確認](pr-preflight.md) を参照します。Hook が利用できなくても同じ判断を手順で行います。

## 削除

完了にした変更では記録を削除しません。`done` の最終記録が取り込み先に入った後の、別の変更で削除します。squash merge などでは、同じ変更で作成・更新して削除した記録が取り込み先の履歴に残らないためです。取り込み方法は利用先の運用に任せます。

次の条件をすべて満たす記録だけを削除できます。Plugin ルートの `scripts/wip.py sweepable --repo <対象> --base <取り込み先>` が `deletable` と判定するものに当たります。

- 作業ツリーと取り込み先の両方で `status.json` が `done`。
- 記録の内容が、作業ツリーとインデックス（ステージ済みの変更）の両方で取り込み先と一致する。
- Git の管理外のファイル（未追跡・無視対象）がない。

削除の前に、継続して必要な仕様・判断が関連文書へ反映されていることを確認します。記録への参照は、反映先か、取り込み先のコミットを固定した URL に付け替え、削除と同じコミットに含めます。

## 削除した記録の参照

マージをまたいだ記録は、通常の `git log -- <パス>` に表示されないことがあります。`git log --full-history -- <パス>` で探し、削除コミットの親から取り出します。再開する場合は `wip/` に復元します。
