## 現在の設計

- `sdd`: 要求・設計を合意し、仕様に基づく実装・検証と SOT の維持を担う。
- `steering`: 相談・判断・進捗の記録と、セッションを跨ぐ再開を担う。
- 相互の実行を必須にせず、既存の仕様・作業記録があれば参照する。
- 作業の保存先は `.hq/v2/work/`。
- 要求・設計・タスクは別ファイルを標準案にする。短い内容は `work.md` 内で節を分けて統合できる。構成は未確定であり、ユーザーのレビューに従って変更できる。
- ファイル数とは別に、ユーザー要求、提案・仮定、合意済みの決定を区別する。
- SOT は PRD・FDS・ADD を必須の役割、REPO・DEV・GLOSSARY をオプショナルとして記載する。既存の同等文書を尊重する。

## 変更の根拠

ユーザーは Skill の名称と作業記録の保存先を指定した。名称は `sdd` と `steering`、現在の保存先は `.hq/v2/work/` とする。作業記録はプロジェクトを跨いで再利用したいという意図を確認済み。

要求・設計・タスクの分割を標準にすることは、ユーザーの疑問に対するエージェントの提案。分割だけで混同は防げないため、各内容の役割と合意状態も記録する。

# HQv2 の方向性と sdd の軽量化

更新日: 2026-10-12（Asia/Tokyo）
状態: 相談中。下記の軽量化案は現行 Skill に未反映。

## ユーザーの意図

HQv2 は Codex と Claude Code で使える開発ノウハウを揃える Plugin。スペック駆動開発は収録する手法の一つ。

以前の HQ では、独自の開発ループが各 Skill の使いやすさと再利用性を損ない、作業時間やメトリクス改善のための負担が増えた。HQv2 では各 Skill を単独で使えるものとし、守る原則と大きな分岐を示して、具体的な進め方はメインエージェントに任せたい。

`docs/wip/` に相談と作業の記録を残し、セッションを跨いで再開する方法を出発点とする。長く維持する文書と作業文書の二つの時間軸、現在の合意を表す文書を SOT とする考え方は残したい。

## 現行構成で重くなる箇所

- 変更開発で要求・設計・タスクの3ファイルを毎回用意する。
- 初期仕様で全体文書を2ファイル用意し、さらに6ファイルへの拡張構成を案内する。
- 利用先の記載例が、機能追加・振る舞いの変更に Skill の使用を必須としている。
- 軽微な変更を軽く扱うには、プロジェクト側に例外規定が必要になっている。

二つの時間軸を保つために、これらの固定ファイル数や一律の適用は必要ない。

## 提案: 原則・プロジェクト規約・Skill を分ける

| 置き場所 | 責務 |
| --- | --- |
| 利用先の AGENTS.md など | 作業ブランチ、PR、必要な検証など、すべての変更に適用するルール |
| sdd | 要求・設計を相談し、合意・進捗を残して再開するための手法 |
| 他の独立した Skill | レビューなど、単独で依頼・完了できる作業。追加は実際の繰り返し依頼を基に判断する |

Skill はプロジェクト規約を確認して従うが、別の Skill の実行や独自の状態管理を前提にしない。ブランチ・PR のルールは規約へ一度書けばよく、それだけのための Skill を増やす必要はない。Skill がそれらを代わりに定義・重複管理しないことが境界になる。

## 提案: 文書は1枚から、必要なときだけ分ける

- 作業記録は既存の `docs/wip/` などを使い、指定がなければ1テーマ1ファイルから始める。
- 1枚に目的、今回の範囲、要求・設計、決定と未決事項、現在地、次の作業、検証結果を必要な分だけ書く。空の見出しを埋めるための作業はしない。
- 長くなり、個別に参照・更新する必要が出たときだけ分割する。3ファイルは選択肢として扱う。
- 長く維持する仕様も、次の作業の判断に必要な合意を1枚から残す。初期に網羅的な要求・設計文書を揃えない。
- 作業記録を必ず作るのではなく、後で再開する必要、未決事項、残す価値のある判断があるときに作る。明確で短時間の修正は依頼と差分・PRで十分な場合もある。

ファイル数を減らしても、必要な要求・設計をまとめて合意してから実装する原則は保つ。依頼や既存の記録に必要な合意があれば、形式的な確認を追加しない。

## 提案: SOT は現在の合意を表し、変更可能にする

SOT の役割は参照先を一意にすること。過去の決定を変更できなくすることではない。

- 確定したこと、仮置きしたこと、未決事項を区別する。仮説を合意済みの仕様として扱わない。
- 方向転換は作業文書で差分・理由・影響を相談し、合意した範囲を SOT に反映する。
- 要求や制約の変更はユーザーと確認する。合意範囲内の実装上の判断はエージェントに任せる。
- SOT と実装が異なる間は、その差と未反映の状態を作業文書に残す。過去の作業文書は履歴であり、現在の SOT を上書きしない。
- 完了時は残す価値のある仕様・制約・判断を SOT に反映する。検討過程や完了タスクをすべて転記しない。

## 提案: アイデアは実装の約束にしない

まず `docs/ideas.md` のような1枚に、思いつき、期待する価値、確かめたいことだけを置く。優先順位・期限・詳細設計は必要になるまで付けない。

試したくなったら作業文書を用意して「何を確かめれば採用判断できるか」を相談する。実験したことは製品への採用を意味しない。採用した内容だけを SOT へ反映し、元のアイデアには作業へのリンクを残す。アイデアが増えて扱いづらくなったらテーマ別に分ける。

アイデアは時間軸をもう一つ増やすというより、まだ合意されていない情報の置き場として扱う。

## タスクごとの判断例

| 状況 | 記録・相談の目安 |
| --- | --- |
| 明確なタイポ修正 | 作業文書を省略できる。プロジェクトのブランチ・PR・検証規約は守る |
| 小さく明確な機能変更 | 依頼に要求・設計上の合意があれば進める。判断や再開が必要なら短い作業メモを残す |
| 未確定な機能追加・大きな改修 | 作業メモで要求・設計・影響を整理し、必要な合意を得る。長くなったら分割する |
| 技術や機能の実験 | 確かめる問いと終了条件を記録する。採用判断は実験結果を見て行う |

分類名や変更行数で一律に工程を割り当てず、不確実性・影響・再開の必要から判断する。

## 次の相談と実装候補

推奨する落とし所は「文書で相談と再開を支える Skill」。全開発を統括する固定ループにはしない。

次に決めるのは、作業文書1枚を標準にすることと、未指定時の保存先を `docs/wip/` にすること。合意後、SKILL.md、参照文書、テンプレート、利用先の記載例、README を一緒に更新する。現行の `.steering/` や3ファイル構成を利用するプロジェクトはそのまま扱えるようにする。

今回反映済みなのは Plugin の目的・説明文と、Plugin のメンテナンス指示の範囲。軽量化の手順とテンプレートは未変更。
