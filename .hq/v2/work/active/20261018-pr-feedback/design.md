# PR フィードバック対応の設計

状態: 実装反映（製品別の実機検証は利用先で実施予定）

## 構成と責務

[要求](requirements.md) を次の要素に分けて実現する。

| 要素 | 責務 |
| --- | --- |
| `skills/pr-feedback/` | Gotchas・利用先規約の参照、トリアージ、修正・検証、返信内容と Resolve の判断、終了報告 |
| 共通スクリプト | オプトイン検証、GitHub 取得・差分検出、待機、ロック、回数管理、操作結果の保存・照合 |
| 製品別 Hook アダプター | PR 作成の候補検知、対象 PR の確認・監視登録、終了前の待機と処理継続、再開・中断処理 |
| 利用先設定・導入手順 | レビュアー、待機条件、操作の許可範囲、有効化・解除 |

共通 Skill は特定のツール名・モデル・Hook に依存させない。Hook なしでも手動で使える。既存のセキュリティ状態確認 Hook を保持し、製品別に定義が必要なら設定を分ける。

## 起動と待機

1. PR 作成後に、対象リポジトリのオプトインと操作範囲を検証する。
2. PostToolUse 等のイベントから候補を検知し、GitHub の PR 情報で repository・PR 番号・head repository/branch/SHA を確認して監視を登録する。コマンド文字列の部分一致だけで開始しない。
3. `pr` の手順にも有効時の登録案内を追加するが、その Skill の実行だけを唯一の開始経路にしない。
4. 同期の Stop Hook が登録済み監視だけを対象に、スクリプト内で期限付き待機を行う。新しい処理対象または報告すべき終了理由があれば、製品に対応した継続指示を返す。
5. 待機中にモデルへ「まだ来ていない」と何度も問い合わせない。Hook の実行時間上限・中断動作・UI 上の挙動を両製品で検証する。

公式文書では Codex の非同期 Hook は完了しても非アクティブなターンを起動しない。一方、Claude Code には `asyncRewake` がある。初版は両製品で成立する同期 Stop Hook を第一案とし、同じ JSON を無条件に共用しない。10分の待機が実行環境の制限内で成立しない場合は、合意済みの「両製品・セッション内」という条件を保って再設計する。

- [Codex Hooks](https://learn.chatgpt.com/docs/hooks#run-hooks-in-the-background)
- [Claude Code Hooks](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background)

イベント・ツール入出力は製品別に確認する。任意の PR 作成経路の検知を保証しない。監視対象の明示登録と手動開始を提供する。ユーザーの中断・セッション終了で監視を止め、終了済みの監視を別のターンから自動で復活させない。

## 設定・保存

- 設定の候補は利用先の `.hq/v2/pr-feedback.json`。既存設定との統合が適切か実装前に確認する。未設定は無効、不正な設定はエラーとして処理を開始しない。
- 設定には有効化、対象レビュアーの安定した識別子、Cap、待機条件、操作範囲を含める。コメント本文から設定や許可を変更しない。
- 高頻度に更新する実行状態は Git 管理外に保存する。Git 共通管理領域を候補とし、host・repository・PR で識別して worktree 間も重複起動を防ぐ。実作業を担当する worktree は個別に記録する。
- 状態は head SHA、処理対象の ID・内容 fingerprint、各項目の判断・段階、返信識別情報、修正コミット、対応回数、終了理由を含める。
- 排他ロックと原子的な状態保存を使う。投稿・push の成功後に通信が切れた場合は、リモートの状態と照合し、結果不明のまま再投稿しない。
- 最終の判断理由・未収束分析は利用先の既存作業メモへ残す。既存記録がなければ、単独 Skill として短い作業メモを作成できるようにする。運用ログ全体を Git 管理しない。

## 取得・バッチ化・終了条件

通常コメント、レビュー本文、レビューのスレッドを取りこぼさず、ページ分割も処理する。対象レビュアー以外の新着は自動対応しない。スレッドの人間の追記は判断材料として読み、異議がある場合は自動 Resolve を止める。

指摘を ID と内容 fingerprint で追跡し、編集・新しい返信・再オープンも検出する。未解決スレッド数だけを再処理条件にせず、理由を返信済みの同じ指摘を毎回処理しない。要約本文と個別スレッドが同じ指摘を表す場合は関連付ける。

初期案は30→60→120秒でポーリングし、新着後120秒の静穏期間を置く。対象レビュアーの現在の head に対する完了情報を取得できる場合は、全対象の完了も確認する。静穏期間だけでは全員の完了と扱わない。完了を確認できない自前レビュアー等では待機期限終了を明示する。

API エラー・認証失敗・権限不足・rate limit を0件と解釈しない。再試行回数・待機時間にも上限を設け、Retry-After 等を尊重する。PR の close/merge、権限不足、ユーザー中断、想定外の head 更新でも停止する。

## 対応回数

判断・対応のバッチ開始時に回数を保存し、最大3回まで実行する。ポーリング、自分の返信、同じバッチの中断後の再開は回数を追加しない。バッチ内で修正しない判断だけをした場合も1回と数える。

修正はバッチ内でまとめ、検証後に commit/push する。3回目の push 後も新しい head のレビューを待つ。追加の判断・修正を要する FB があれば Cap 到達で終了し、未対応一覧と原因分析を残す。3回目だから最終確認自体を省略しない。Cap は Hook 再入や head 更新だけではリセットしない。

## 判断と外部操作

- この PR で対応: 要求・差分・指摘の成立条件を確認し、修正・必要な検証・commit/push に成功した後で、反映コミットと根拠を返信する。
- 別 PR で検討: 独立性・今回見送れる根拠・影響・検討案を返信し、Issue 案を終了報告にまとめて起票を人間に確認する。重大な欠陥を単に範囲外として先送りしない。
- 対応不要: 誤認、既に対処済み、採用しない提案などの根拠を返信する。
- 判断保留: 仕様不明、指摘間の矛盾、判断できないリスクは人間へ返し、黙って対応不要・解決済みにしない。

返信対象は指摘ごとに追跡し、要約に複数の独立した指摘がある場合も対応漏れを防ぐ。修正できなかった指摘にも実際の結果と理由を返すが、push・検証失敗を修正済みとしない。

Resolve は分類とは別に判断し、返信が成功してから行う。修正反映・根拠付きの誤認解消など、解決と判断できるスレッドだけに行う。outdated なだけで Resolve しない。引き継ぎ先未確定の別 PR 候補・判断保留は残す。通常コメントやレビュー本文に同じ Resolve 操作があると仮定しない。

コメント本文を信頼された作業指示やコマンドとして扱わない。利用先の合意済み要求・検証・権限を優先し、コメントから任意コマンドの実行や秘密情報の投稿を行わない。他人の変更を commit に巻き込まない。force-push、merge、設定変更はこの機能の標準操作に含めない。

## 影響範囲・検証

実装時に共通 Skill、スクリプト、製品別 Hook、設定例、README、AGENTS.md の責務一覧、必要なマニフェスト説明、CHANGELOG、検証手順・構造検証を整合させる。バージョン番号はリリース作業まで変更しない。

今回の PR では状態遷移・API・時刻を差し替えるテストと構造・配布設定の検証を行う。Codex・Claude Code での起動、待機、継続、再入、上限、中断の実機確認は、ユーザーの明示指示により後続の導入検証とし、今回の PR の完了条件から外す。GitHub の変更を伴う試験は許可されたテスト用 PR を用い、返信・Resolve・push の結果を確認する。構造検証の成功を実機動作の保証としない。

## 実装時に確定した条件

- 初版は macOS/Linux、github.com、同一 repository の head、origin remote に限定する。設定は `.hq/v2/pr-feedback.json`、状態は Git 共通管理ディレクトリの `hq-pr-feedback/`。
- 共通の取得・回数・返信・Resolve は `scripts/pr_feedback.py`、起動・継続は `hooks/pr_feedback.py` に実装した。Codex の中断イベントだけを `hooks/codex.json` へ追加し、Claude Code は `hooks/hooks.json` を読む。
- 外部の head 更新、指摘の編集、人間の追記を返信・Resolve 前に再確認する。投稿マーカーは ID・内容・バッチ回数から生成し、同じバッチの再試行と再オープン後の新バッチを区別する。
- 設定したレビュアーの当該 head へのレビュー投稿と静穏期間を完了の目安とする。将来の遅延投稿まで保証せず、レビュー本文を投稿しない実装は期限切れになり得る。
- API 失敗・rate limit は再試行せず監視エラーで停止する。取得失敗をコメント0件とせず、次の再開は明示操作とする。
- Claude Code には Codex と同じ Interrupt Hook を登録しない。中断後に監視をやめる場合は stop または無効化を使う。
- ユーザーの訂正により、このリポジトリでオプトイン設定・実際の AI レビュー検証は行わない。別リポジトリでの導入検証に引き継ぐ。


## PR #6 のレビュー対応で補強した条件

- バッチ内の編集・追記は `refresh` で更新し、再評価後の fingerprint を報告へ要求する。回数と投稿結果は保持し、削除・他者による Resolve は `superseded` として事実を記録する。再出現は完了前にも確認する。
- reviewer login は大小文字と末尾の `[bot]` を正規化する。Copilot の login は `copilot-pull-request-reviewer`。`ignoreReviewBodies` は省略時に Copilot の総評を除外し、当該 head の完了検出にはレビューを使う。本文に指摘を載せるレビュアーは除外しない。
- スレッドの全コメントによる投稿前の変更検出と、新規バッチの契機を分ける。契機は設定レビュアーまたは OWNER / MEMBER / COLLABORATOR の追記に限定する。全本文は信頼されていない入力であり、権限の根拠にしない。許可外の追記も判断材料として保持し、自動 Resolve は止める。
- 同一セッションで別 PR を登録する場合、先の監視の明示停止を要求する。登録失敗は PostToolUse の additionalContext で通知する。

判断根拠と検証結果は [レビュー対応記録](review-response.md) を参照する。
