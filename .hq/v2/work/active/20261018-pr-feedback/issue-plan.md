# PR フィードバック監視の不具合対応計画

状態: 両 Issue の実装・自動検証済み。対象製品内の実機検証待ち。2026-10-21、ユーザーは設定名を `waitAfterPush` とすることに合意し、「それで計画直して対応進めてくれる？」と実装の続行を依頼した。既存の計画に沿って Issue #9・#10 を対応する。

## 対象と確認結果

- [Issue #9](https://github.com/tom-e-kid/hqv2/issues/9): macOS のスリープ後に Stop Hook が打ち切られ、監視が `waiting` のまま残る。実機での発生状況は Issue の報告に基づく。こちらでは再現未実施。
- [Issue #10](https://github.com/tom-e-kid/hqv2/issues/10): 初回しかレビューしないレビュアーを、push 後も現 head のレビュー完了条件に含め、毎回期限切れまで待つ。
- GitHub の open Issue 検索でこの2件を確認した。両 Issue とも追加コメントなし。
- `hooks/pr_feedback.py` は同期 Stop Hook 内で待機し、スリープ抑止や異常終了後の検出処理がない。`status` は保存状態を返すだけである。
- `scripts/pr_feedback.py` はレビュアーを文字列の配列に限定し、全員の現 head に対する投稿済みレビューを要求する。Issue #10 の条件では、初回レビューのみのレビュアーが完了条件を満たせなくなることをコードで確認した。

既存の[要求](requirements.md)・[設計](design.md)を基準とする。期限切れを収束と扱わないこと、最大3回、投稿の重複防止、対象外の head 更新で停止すること、セッション終了後の常駐監視を設けないことを維持する。

## 対応順序と分割

1. Issue #9: スリープの予防と、監視が中断した状態の可視化を先に実装・検証する。
2. Issue #10: レビュアーの設定と完了判定を変更する。
3. 両方を組み合わせた回帰確認と、対象製品での導入検証を行う。

修正は Issue ごとに別 PR とし、いずれも最新の `develop` から作業ブランチを作成して `develop` へ取り込む。計画作成時のブランチは `docs/pr-feedback-issues-plan`。実装は `fix/pr-feedback-interruption`（#9）と `fix/pr-feedback-wait-after-push`（#10）に分ける。

## Issue #9 の設計案

- macOS の Stop Hook で実際に待機する期間に限定して、`caffeinate -i -w <Hook PID>` を起動する。共通 Skill に macOS 固有の手順を埋め込まず、Hook 側に配置する。他 OS では起動しない。
- 正常終了・例外時は子プロセスを終了・回収する。Hook が強制終了した場合も、監視対象 PID の終了に連動してスリープ抑止が残らないことを実機で確認する。起動失敗は通知し、監視本体は期限付きで継続できるようにする。
- 監視の実行中かを判別する実行ロック等と、最終取得成功時刻・監視実行情報を用意する。`lastChange` は新着内容の変化時刻なので、生存確認に流用しない。プロセス強制終了でロックが解放される方式を優先する。
- `waiting`、期限超過、期限後の取得成功なし、実行主体なしを照合し、中断の疑いを `status` で可視化する。期限超過だけで、実行中の API 取得や正常な期限終了を「Hook の強制終了」と断定しない。
- 次の Stop Hook では、該当状態を中断・未確認として一度報告する。明示的な `register` では中断情報を返し、再開時に回数・処理済み項目・未完了のバッチを保全する。詳細な終了理由名と保存形式は実装時に確定する。
- Hook がスリープから復帰して実行を続けられる場合は、wall clock の永続 deadline を再評価し、待機時間を延長しない。最新取得が可能ならフィードバックを取得し、確認できない場合は収束としない。
- セッションも Hook も動いていない間の即時通知は対象外。次の `status`・Hook・明示登録時に検出する。

受け入れ条件:

- アイドルスリープを待機中だけ抑止し、Hook 終了後に抑止プロセスが残らない。
- 強制終了後も保存データを壊さず、次回確認で中断の疑いと未取得の可能性を示す。
- 稼働中の監視、API 失敗、通常の待機期限終了を誤って同じ終了状態にしない。
- 再開で Cap をリセットせず、返信・Resolve を二重実行しない。

## Issue #10 の設計案

設定例:

```json
"reviewers": [
  {"login": "copilot-pull-request-reviewer", "waitAfterPush": true},
  {"login": "custom-reviewer", "waitAfterPush": false}
]
```

- 既存の文字列指定は `waitAfterPush: true` と同じ意味で受け付ける。オブジェクトでも省略時の既定値は true とし、真偽値以外は拒否する。login の正規化後の重複・矛盾も拒否する。
- 読み込み時に設定を正規化する。指摘の取得、完了検出、人間の追記判定、Resolve の許可判定など、レビュアー一覧の全利用箇所を対応させる。
- `waitAfterPush: true` は現 head に対する投稿済みレビューを必要とする。false は同じ PR 内で1回以上の投稿済みレビューがあれば完了条件を満たす。false でも初回レビュー未到着なら待つ。下書きや取り消されたレビューを完了としない。
- 完了条件から外れたレビュアーも、新規指摘・編集・追記の取得対象からは外さない。レビュー本文の無視設定も、完了確認とは引き続き分離する。
- 全員の設定に応じた完了確認と静穏期間が成立したら、未処理があればバッチ化し、なければ収束する。期限切れや API 失敗は収束の根拠にしない。
- 既存の状態ファイルを読み込めるようにし、設定変更や再開によって処理回数・処理済み項目を消さない。古い状態への既定値適用を検証する。

Issue の「レビュー開始イベントがなければ、これ以上レビューは来ない」という案は採用しない。開始イベント不在は、イベント遅延・取得漏れ・未対応のレビュアーと区別できないためである。

進行中イベントへの対応は別の小段階で判断する。実際の取得結果と公式 API の仕様で、レビュアー、対象 head、開始・完了・再要求を対応付けられるか確認する。対応付けが確認できた場合のみ、進行中のレビューを完了判定への追加の待機条件として使う。イベント不在だけでは待機を省略しない。この確認が成立しなくても、明示した `waitAfterPush` 設定による修正を先に完了できる。

受け入れ条件:

- 初回のみのレビュアーと毎 push のレビュアーが混在しても、再レビュー完了と静穏期間の後、期限を待たずにバッチ化・収束できる。
- 初回レビュー未到着、現 head のレビュー未到着、静穏期間未成立では収束しない。
- false のレビュアーからの追加指摘も取得し、既存の再処理・上限の規則に従う。
- 文字列設定で従来の完了条件と対象判定を維持する。
