# コミット前のセキュリティチェック

状態: 要求・設計を合意し、実装・検証済み。このリポジトリにも導入済み。develop への取り込み前。
作業ブランチ: feat/commit-security-check
取り込み先: origin/develop

## 要求

- コミットするファイルに含まれるローカル環境の具体的なパスを検出する。
- 環境変数ファイルの誤登録を検出する。
- API キー・トークン等の秘密情報と思われる値を検出する。
- スクリプトで判定できる範囲をコミット前に自動実行し、検出時はコミットを停止する。
- HQ Plugin から提供し、このリポジトリにも適用する。

## 合意と実装

### 検証対象と判定

利用者は Plugin の導入後、リポジトリ単位で明示的に有効化する。スクリプトを利用先へコピーし、更新も明示的に行う方式で合意した。Python 標準ライブラリと Git を使う共通スクリプトを配布する。追加の Python パッケージやネットワーク接続を通常実行の前提にしない。

- 作業ツリーではなく、Git index にあるコミット対象のファイル名と内容を読む。追加・変更・コピー・名前変更を対象にし、削除済みファイルは内容検証から除外する。部分ステージ・初回コミット・空白や改行を含むファイル名・worktree を考慮する。
- 差分の追加行だけでなく、対象ファイルのステージ済み内容全体を確認する。未変更ファイル全体や過去の履歴を監査する機能とは分ける。
- `.env`・`.env.*`・`*.env`・環境変数のローカル設定など、実値を保存するファイル名を拒否する。`.env.example`・`.env.sample`・`.env.template` など明示的な雛形名は名前だけでは拒否せず、内容は引き続き検証する。単に `env` ディレクトリであることは拒否理由にしない。
- macOS・Linux・Windows のユーザーディレクトリ等の具体的なローカル絶対パスを検出する。すべての絶対パスを拒否するものではなく、`/usr/bin` のような共有のシステムパスや環境変数による参照と区別する。
- 秘密鍵のヘッダー、代表的なサービス固有のキー・トークン形式、および API キー・トークン・パスワード等への具体値の代入を規則で検出する。明示的なプレースホルダーと変数参照は区別する。任意の未知形式の秘密値を完全に検出する保証はしない。
- 検出時はルール名・リポジトリ相対のファイル名・行番号だけを通知し、該当行・秘密値・ローカル絶対パスを出力しない。Git 読み取り失敗や競合中等で検証できなければ成功扱いしない。
- テストや文書で必要な例外は、利用先で Git 管理する明示的な設定でルールと対象を限定し、理由を残す。設定は `.hq/v2/security.json` の version 1 とし、path・rule・fingerprint・reason を指定する。テキスト検出は該当行の SHA-256、ファイル名・検証不能は Git object ID に限定する。秘密値そのものを例外設定へ転記しない。ファイル全体を一律に除外する回避策を標準にしない。
- バイナリや検証不能な形式を黙って検証済みとせず、検証範囲・除外条件を文書と結果に明示する。

### コミットを止める経路

Git の `pre-commit`・`pre-merge-commit`・`pre-applypatch` hook から共通スクリプトを実行する。これにより、エージェント以外のターミナルや GUI から通常の Git commit を行う場合も同じ判定を使う。

Plugin の `PreToolUse` 単独では、`git add && git commit` 実行前の index や別のターミナルでの操作をカバーできない。そのため、Plugin のライフサイクル Hooks は Git hook の導入状態の確認・案内を補助し、コミット直前の判定は Git hook が担当する。

利用先への Git hook 導入は明示的なセットアップ操作で行う。Plugin を読み込んだだけでは Git 設定を変更しない。既存の `core.hooksPath`・hook がある場合は上書きせず、既存管理方法への組み込みを案内する。実際の配置と更新方法を文書化し、Plugin の移動・削除でスクリプト参照が切れた場合もコミットを通さない。

このリポジトリでは既存の `core.hooksPath` と対象 Hook は確認されなかった。`scripts/setup_security.py install` で Git 共通管理ディレクトリへ検証コードをコピーし、3種類の Hook をローカルに有効化した。状態は `ready`。全利用者へのグローバル設定は変更しない。

Git hook は `--no-verify` や設定変更等で回避できるため、改ざん耐性のある強制機構とは扱わない。通常の作業では回避しない方針を規約に記載する。将来の必須 CI 化は今回の範囲外とする。

### Plugin と関連文書

Codex・Claude Code はともに Plugin の `hooks/hooks.json` と `SessionStart`・`PreToolUse` を提供する。ただし、対応バージョン・trust・入力形式を製品ごとに確認する。共通判定ロジックを複製せず、今回の配布は両製品共通の `SessionStart` のみとし、導入状態の確認を行う。両製品の互換環境変数を使う同じ設定とハンドラーで対応する。

README に Hooks の対応製品・役割・セットアップを追加する。専用の検証文書に手動実行・検出範囲・制約・失敗時の対処を記載する。git Skill・利用先の記載例・このリポジトリの Git 規約・構造検証・CHANGELOG を整合させる。共通 Skill 自体は Plugin Hooks の存在に依存させない。

## 検証計画

- 隔離した Git リポジトリで正常系と各検出規則の失敗系を確認する。
- 作業ツリーのみ修正しても、index に残る問題を検出することを確認する。
- 初回コミット・名前変更・削除・特殊なファイル名・worktree・読み取り失敗を確認する。
- 実際の Git hook 経由で問題のあるコミットが作成されず、正常なコミットが成功することを確認する。本リポジトリに試験用コミットを作成しない。
- エラーメッセージに秘密値や該当行が出ないことと、既存 hook を破壊しないことを確認する。
- Plugin 設定は両製品で確認し、未実施の範囲は明記する。

## PR の分離

検証文書の切り出しとは別の作業ブランチと PR にする。単独で利用・検証できるよう、検証手順の参照は既存の README の検証節を使い、別 PR で新設する docs/validation.md には依存しない。

分離後の単独ブランチでも23件の自動テスト・構造検証・両製品の配布設定検証が成功した。文書切り出し側のコミットを含めずに検証している。
