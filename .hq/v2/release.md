# HQ のリリース規約

## 対象とバージョン

設定は [settings.json](settings.json)。`develop` に公開候補を集め、リリース時に `main` へ取り込む。利用者に影響する変更は、通常の作業 PR とともに [CHANGELOG.md](../../CHANGELOG.md) の `Unreleased` に記載する。公開履歴を新設時の推測で埋めず、初回リリースは既定の `2.0.0` とする。

以降は SemVer を使い、既存の Skill の利用方法・保存形式・対応環境などの互換性への影響から判断する。互換性を壊す変更は major、互換性のある機能追加は minor、修正は patch。コミットの type だけでは確定しない。移行が必要な変更には、その条件と手順を記載する。

## 準備と取り込み

1. 前回の公開タグ・Release と今回の差分を確認し、公開対象とバージョンを確定する。初回は公開済みのバージョンがあると仮定しない。
2. `develop` から `chore/prepare-release-<version>` を作る。対象の `Unreleased` を `## [<version>] - YYYY-MM-DD` の節に移し、空の `Unreleased` を先頭に残す。日付は Asia/Tokyo の公開予定日とし、延期した場合は見直す。
3. `.codex-plugin/plugin.json` と `.claude-plugin/plugin.json` の `version` を同じ値へ更新する。両カタログには現在 version 項目がないため追加しない。README の「第2世代の開始バージョン 2.0.0」は履歴上の説明なので更新しない。現在のバージョンを明記した呼び出し例などがあれば整合を確認する。
4. [Git 規約](git.md) のリリース検証を行い、準備 PR を `develop` へ取り込む。
5. `develop` から `main` へのリリース PR を作り、同じ条件を確認して取り込む。準備開始から取り込みまでは次回向けの変更を `develop` に入れない。対象の追加・変更が必要なら、範囲を合意し直して検証する。

`main` 側だけで緊急修正した場合は、その変更とバージョン・CHANGELOG を `develop` へ反映してから次のリリースを準備する。main／develop 間の PR はマージコミットを使って共通の履歴を保ち、同じ差分を繰り返し取り込まない。

## タグと公開

`main` に取り込まれた対象コミットへ注釈付きタグ `v<version>` を付け、確定した remote へそのタグを送る。GitHub Release はそのタグを対象に作成し、該当バージョンの CHANGELOG を説明に使う。タグは `main` の検証済みコミットを指すことを確認する。

タグ・Release・配布済みバージョンの上書きはしない。中断後は各公開先の状態を確認し、未完了と確認できた段階だけを再開する。Plugin の公開方法を追加する場合は、その手順と検証を先にこの規約へ記載する。接続・認証の問題で公開結果を確認できない場合は、ローカルの準備完了を公開完了とは扱わない。
